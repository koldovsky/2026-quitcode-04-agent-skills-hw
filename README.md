# QuitCode Workshop 4 — домашнє завдання (Agent Skills)

Стартовий репозиторій четвертої домашки курсу QuitCode **«Modern Development with Agentic AI»**.

> Воркшоп 4: **Agent Skills: упаковка експертизи команди**
> Автор: В'ячеслав Колдовський — Dev AI Consulting (dev-ai.dev)

WS3 закінчився правилами й командами: короткі домовленості, які агент бачить завжди. Сьогодні —
скіли (skills): теки з інструкціями, довідкою й скриптами, які агент підтягує тоді, коли задача
їх потребує. Ви поставите чужий скіл так, як ставлять залежність у клієнтський проєкт (з рев'ю й
закріпленою версією), упакуєте два шматки експертизи команди у власні скіли — і перевірите
A/B-прогоном, чи скіл справді змінює те, що робить агент. ~3 години.

## LeadDesk — що це і навіщо

`LeadDesk` — портал для клієнта агенції, студії Studio Nova: публічна форма заявки, яка передає
лід у n8n, демо-вхід для команди, дашборд лідів зі статистикою, пошуком, експортом в Excel і
графіком джерел. Саме такими будуть перші кодові проєкти QuitCode: Next.js-форма або портал поверх
автоматизації, яка вже працює в n8n.

Застосунок працює, але написаний так, як його «швидко згенерував агент»: дашборд відкривається
повільно, форма чекає n8n, у браузер потрапляє зайве, а виклик n8n не відповідає домовленостям
команди. Знайти й виправити це — частина завдання, тож конкретних місць тут не перелічено.

| Шлях | Що це |
|---|---|
| `app/`, `components/`, `lib/` | Застосунок: Next.js 16.3.5 (App Router), React 19.2, TypeScript, Tailwind v4 |
| `lib/db.ts` | «База» в пам'яті: ~200 синтетичних лідів, штучні затримки запитів і лічильники `db:<запит>` у журналі сервера |

Усі дані синтетичні: люди, компанії й адреси вигадані, домени — `*.example.test`, значення
секретів у прикладах — `change-me-…`.

## Швидкий старт

Потрібно: Node.js ≥ 20.9, Git (на Windows — Git Bash), GitHub CLI (`gh`), Claude Code або Cursor.

```bash
gh repo fork koldovsky/2026-quitcode-04-agent-skills-hw --clone
cd 2026-quitcode-04-agent-skills-hw
git checkout -b ws04/<github-username>
npm install
cp .env.example .env.local
npm run dev                      # http://localhost:3000
```

В іншому терміналі (з кореня репозиторію):

```bash
node tools/mock-n8n.mjs          # «n8n» на http://127.0.0.1:5678
```

Далі — [`docs/walkthrough.md`](docs/walkthrough.md): налаштування, кроки до кожного завдання,
команди для Windows + Git Bash.

## Як це оцінюється

Рубрику опубліковано **наперед** — прочитайте її до того, як почнете. Definition of Done нижче —
залік/незалік; рубрика — якість роботи на 100 балів.

| Вимір | Балів | Що саме дивимось |
|---|---|---|
| **Сторонній скіл** (Task A) | **20** | `docs/skill-review.md` за чеклістом і **до** встановлення: перегляд без встановлення, скрипти, мережа, `allowed-tools`, аудити, ліцензія, як закріплено версію. Встановлено з тегом і `--copy`: справжні файли в `.claude/skills/vercel-react-best-practices/` і `skills-lock.json` у git. ≥ 3 виправлення — кожне окремим комітом з id правила. Числа до/після з продакшн-збірки. Кожну пораду звірено з документацією Next.js 16. |
| **Скіл лише з інструкцій** (Task B) | **15** | `name` = назва теки; `description` каже, що робить скіл і коли його застосовувати, і містить фрази, якими команда справді формулює задачу. Конкретний патерн: Server Action з перевіркою сесії й валідацією всередині, `useActionState`, доступні помилки полів, дія повертає лише `{ status, … }`, жодних персональних даних у журналах, повільне — в `after()`. Посилання на правила Vercel за id, а не їх копія. Розділ Verify. Спрацювання на звичайний запит у свіжій сесії записане в `docs/verification.md`. |
| **Скіл з довідкою й скриптами** (Task C) | **35** | Записку перетворено на скіл, а не скопійовано: у `SKILL.md` — стислий контракт, чекліст, правила зупинки, перевірка; деталі — у `references/`, прямі посилання з `SKILL.md`. `scripts/check-contract.mjs`: Node без залежностей, ≥ 5 перевірок з id, PASS/FAIL на кожну, для FAIL — файл:рядок, ненульовий код виходу при FAIL, `--root <тека>` і `--help`; знаходить порушення в коді `main` і дає 0 FAIL на фінальному коді. «Запит на кошторис» працює з моком: форма відповідає швидко, n8n отримує запит за контрактом, підписаний колбек приймається. Запит, на який спрацював скіл, вивід `check-contract.mjs` і журнал мока — у `docs/verification.md`. |
| **A/B-перевірка** (Task D) | **25** | Один запит без змін, дві свіжі сесії, та сама модель і рівень міркування; у прогоні A скіла з Task C немає в копії проєкту; `materials/`, `docs/`, `README.md`, `.coderabbit.yaml` і `.github/` немає в обох. Для кожного прогону: які скіли бачив агент, чи викликав скіл, вивід `check-contract.mjs`, журнал мока, час відповіді форми, що потрапило в журнал сервера, змінені файли й діф у `docs/ab/`. Таблиця порівняння й висновок, що спирається на ці спостереження. Чесне «різниці немає» з поясненням, звідки агент узяв домовленості, — повноцінний результат. |
| **Бонус** (Task E) | **5** | Один з варіантів зроблено й задокументовано: рев'ю пакета n8n-скілів за тим самим чеклістом без встановлення; тест спрацювання (запити, на які скіл має й не має спрацьовувати) з результатами; перевірка тих самих скілів у Cursor. |

### Що знімає бали

- Встановлення без рев'ю або рев'ю, написане вже після встановлення; версія без тега чи SHA.
- Junction чи symlink замість справжніх файлів; друга копія скіла в `.agents/skills/`.
- Виправлення без id правила або без чисел; порада скіла, застосована всліпу, хоча в Next.js 16
  вона не діє або шкодить.
- `name` ≠ назва теки; `description` без «коли застосовувати»; `SKILL.md`, що дослівно копіює
  записку чи правила Vercel.
- `check-contract.mjs`, який ніколи не бачив поганого коду (завжди PASS), або без коду виходу.
- Справжні секрети в git (у `.env.example` секрети — лише `change-me-…`); тестовий URL вебхука
  (`/webhook-test/`) у коді чи `.env.example`.
- A/B з різними запитами, без свіжих сесій, зі скілом, лише перейменованим чи залишеним в
  особистій теці, з видимою агенту запискою чи документацією з контрактом; висновок без даних.
- Зміни в `tools/**`, `materials/**`, `.coderabbit.yaml` чи `.github/**`.

## Definition of Done

- [ ] Три скіли в `.claude/skills/`: `vercel-react-best-practices` (закріплена версія, справжні
      файли в git, `skills-lock.json`), `building-client-form`, `integrating-n8n-webhooks`;
      у кожного `name` = назва теки і є `description`
- [ ] `docs/skill-review.md` — рев'ю скіла Vercel за чеклістом, зроблене до встановлення
- [ ] `docs/verification.md` — ≥ 3 виправлення з id правила й числами до/після; для кожного
      власного скіла — запит, на який він спрацював, і результат; вивід `check-contract.mjs`
- [ ] `docs/ab-validation.md` — обидва прогони: A — без скіла, B — зі скілом; діфи прогонів —
      `docs/ab/a-without-skill.diff` і `docs/ab/b-with-skill.diff`
- [ ] `npm run build` і `npm run lint` без помилок; `check-contract.mjs` на фінальному коді — 0 FAIL
- [ ] Жодних секретів у git: лише `.env.example`; у ньому секрети (`N8N_WEBHOOK_TOKEN`,
      `N8N_CALLBACK_SECRET`) — `change-me-…`, адреси — локальні (`http://127.0.0.1:5678/webhook`,
      `http://127.0.0.1:3000`), жодного `/webhook-test/`
- [ ] `tools/**`, `materials/**`, `.coderabbit.yaml` і `.github/**` не змінені
- [ ] **В описі PR заповнено «Ім'я та Прізвище»** — обов'язкове поле: GitHub-логін не завжди
      дозволяє вас ідентифікувати, а сертифікат виписується на реальне ім'я

## Здача

```bash
git push -u origin ws04/<github-username>
gh pr create --web
```

Відкриється сторінка нового PR з шаблоном опису. Заголовок — `WS4: Ім'я Прізвище`; у шаблоні
заповніть **«Ім'я та Прізвище»** і відмітьте виконані пункти. Не додавайте `--fill`: з ним опис
береться з комітів, і шаблон з обов'язковим полем не підставляється.

CodeRabbit відрев'ює PR за цим чеклістом (українською). **Якщо рев'ю не з'явилося за кілька
хвилин** — додайте в PR коментар `@coderabbitai review` (публічні репозиторії з малою кількістю
зірок не отримують автоматичних рев'ю; ручний тригер працює завжди).

Питання — у чат курсу. Сертифікат — за умови виконання всіх домашок курсу.
