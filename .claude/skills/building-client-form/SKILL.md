# Клієнтська форма з серверною мутацією

Кожен проєкт агенції починається з форми, і кожен розробник (і кожен агент) робить її по-своєму:
дія без перевірки прав, помилки, яких не чує скрінрідер, `console.log(formData)` з персональними
даними, лист клієнту чи виклик n8n, на який користувач чекає секунди. Це рішення команди, а не
варіант на вибір.

## Коли застосовувати

- Нова чи наявна форма, що надсилає дані на сервер через Server Action (заявка, кошторис,
  зворотний зв'язок, нотатка, налаштування профілю тощо).
- **Не** застосовувати: клієнтський пошук/фільтр без збереження (напр. `components/lead-search.tsx`
  — це локальна фільтрація вже завантажених даних, без мутації), читання даних через `GET`/Server
  Component, чи будь-яка дія, що нічого не змінює на сервері.

## Як робимо

1. **Server Action = публічний ендпоінт.** Перевіряй сесію, права й валідацію **всередині** самої
   дії — не покладайся лише на middleware (`proxy.ts` тут перевіряє лише *наявність* cookie, не її
   дійсність) чи перевірку на рівні сторінки. Дію можна викликати напряму, в обхід UI. Дивись
   правило `server-auth-actions` зі скіла `vercel-react-best-practices`. Для дій, що потребують
   залогованого користувача, — той самий патерн, що й `lib/data.ts`'s `getCurrentUser()`: дістати
   сесію з `cookies()`, звірити з БД, відхилити, якщо немає чи невалідна.
2. **`useActionState` + прогресивне покращення.** Форма працює й без JavaScript (звичайний
   POST-фолбек); стан — `{ status: "idle" | "invalid" | "ok", errors?, ... }`.
3. **Дія повертає лише `{ status, ... }`** — ніколи сирий рядок помилки з БД чи винятку. Порівняй з
   `SubmitLeadState` у `app/actions.ts` — це вже правильний контракт, тримайся його форми.
4. **Доступні помилки полів:**
   - кожне поле — в `<label>`;
   - за помилки: `aria-invalid="true"` на полі, `aria-describedby` вказує на `id` тексту помилки;
   - підсумок усіх помилок форми — в елементі з `role="alert"` (щоб скрінрідер озвучив одразу після
     сабміту);
   - введені значення **не зникають** після помилки (використовуй `defaultValue`, не controlled-скид).
   - (Для порівняння: `components/lead-form.tsx` сьогодні виводить помилки як звичайний `<span>` —
     без `aria-invalid`/`aria-describedby`/`role="alert"`. Не копіюй цей патерн у нову форму.)
5. **Жодних персональних даних у журналах.** Не `console.log`/`console.error` тіла форми,
   email/телефону/імені тощо. Лічильники й факти виконання — можна (див. `lib/db.ts`'s
   `console.count`), самі значення полів — ні.
6. **Повільні побічні ефекти — в `after()`**, не `await` в основному потоці дії: листи, вебхуки
   n8n, аудит-лог (`lib/audit.ts`'s `logAudit`). Дивись правило `server-after-nonblocking`.
   (Для порівняння: `submitLead` в `app/actions.ts` сьогодні очікує `fetch(N8N_WEBHOOK_URL)`
   синхронно всередині дії — саме той антипатерн, якого тут уникаємо.)
7. **Мінімізуй, що серверний компонент передає у форму/клієнтський компонент** — лише поля, які
   реально рендеряться, а не увесь запис цілком. Дивись правило `server-serialization`.

Правила Vercel (`server-auth-actions`, `server-after-nonblocking`, `server-serialization`) — у
`.claude/skills/vercel-react-best-practices/rules/`; посилайся на них за id, не копіюй текст.

## Чекліст

```
- [ ] 1. Сесія/права перевіряються всередині Server Action, а не лише на рівні сторінки/middleware.
- [ ] 2. Форма побудована на `useActionState` і працює без JavaScript.
- [ ] 3. Дія повертає лише `{ status, ... }` (без сирих помилок БД чи винятків).
- [ ] 4. Кожне поле має `<label>`; помилки — `aria-invalid`, `aria-describedby`, підсумок у `role="alert"`.
- [ ] 5. Введені значення не зникають після помилки валідації.
- [ ] 6. Жодних персональних даних (ім'я/email/телефон/повідомлення) у `console.*`.
- [ ] 7. Повільні побічні ефекти (лист, n8n, аудит) — у `after()`, не в основному потоці дії.
```

## Правила зупинки — зупинись і спитай людину, якщо:

- Форма має зберігати дані, для яких у проєкті ще немає моделі/таблиці/поля — не вигадуй схему
  сам, уточни, куди саме писати.
- Незрозуміло, чи потрібна авторизація (публічна форма на кшталт `app/page.tsx` vs форма всередині
  `/dashboard`) — уточни, а не вгадуй рівень доступу.
- Побічний ефект (лист, вебхук) вимагає секрету чи URL, якого немає в `.env.example` — не
  вигадуй значення, спитай, звідки його брати.

## Verify — задача готова, лише коли:

- [ ] `npm run lint` і `npm run build` без помилок.
- [ ] Порожня відправка форми показує помилки полів, і введене раніше не зникає.
- [ ] Форма приймає сабміт без JavaScript (звичайний POST, без `fetch`/`XMLHttpRequest` з клієнта).
- [ ] Виклик дії без дійсної сесії (де сесія потрібна) коректно відхиляється, а не падає з 500.
- [ ] У журналі сервера після тестової відправки немає значень полів форми (лише факт виконання).
