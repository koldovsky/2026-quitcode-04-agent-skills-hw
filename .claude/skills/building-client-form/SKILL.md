# building-client-form

Кожен розробник (і кожен агент) робить форму по-своєму: дія без перевірки прав, помилки, яких не
чує скрінрідер, `console.log(formData)`, лист клієнту, на який користувач чекає секунди. Це — один
патерн форми для всіх форм проєкту, звірений з наявною `components/lead-form.tsx` + `app/actions.ts`.

## Коли застосовувати

- Нова форма (публічна чи в дашборді): заявка, кошторис, нотатка, налаштування, зворотний зв'язок.
- Переробка наявної форми: додається поле, змінюється валідація, додається побічний ефект (лист,
  вебхук, аудит).
- **Не** застосовувати: сторінки без введення даних користувачем; клієнтський пошук/фільтр, що
  нічого не зберігає (див. `components/lead-search.tsx` — це не форма); виклик стороннього API,
  що не проходить через наш Server Action.

## Як робимо

1. **Server Action — єдиний вхід, і сесія й права перевіряються всередині нього**, а не лише в
   рендері сторінки: сторінка може редіректити неавторизованого до логіну, але сама дія — публічний
   POST-ендпоінт, до якого можна достукатись і без сторінки. Дивись `server-auth-actions`
   (`.claude/skills/vercel-react-best-practices/rules/server-auth-actions.md`) — і зверни увагу, що
   в цьому ж репозиторії `updateLeadStatus`/`deleteLead` (`app/actions.ts`) цю перевірку пропускають:
   не копіюй той приклад.
2. **`useActionState`** зі станом на кшталт `{ status: "idle" | "invalid" | "ok"; errors?: {...} }`
   (див. `SubmitLeadState` в `app/actions.ts` як приклад форми стану). Форма — звичайний
   `<form action={formAction}>`, без `preventDefault` і без ручного `fetch` із клієнта: вона має
   працювати, коли JavaScript вимкнено (перевірка нижче).
3. **Валідація — на сервері, всередині дії**, навіть якщо є клієнтська: клієнтська — лише зручність,
   джерело правди — сервер (`noValidate` на `<form>`, як у `lead-form.tsx`, якщо є й клієнтські
   підказки).
4. **Доступні помилки полів:**
   - кожне поле — в `<label>`; при помилці — `aria-invalid="true"` і `aria-describedby="<id
     повідомлення>"` на самому `<input>`/`<textarea>`/`<select>`;
   - над формою — підсумок помилок у контейнері з `role="alert"` (з'являється лише якщо є помилки);
   - **введені значення не зникають** після помилки: не скидай форму й не перезаписуй `value` полів,
     яких стосується помилка.
5. **Дія повертає лише `{ status, ...дані для UI }`** — ніколи повідомлення бази чи виключення як
   рядок (`error.message` з `db`/Prisma тощо): текст користувачу пишемо в самій дії, за кодом
   помилки.
6. **Жодних персональних даних у журналах.** `console.log`/`console.error` — лише ідентифікатори
   (`lead.id`, код помилки), ніколи email, телефон, повне ім'я, вміст повідомлення чи заголовки
   запиту як є.
7. **Повільні побічні ефекти — в `after()`**, після того як дія вже повернула стан користувачу: лист,
   виклик n8n/вебхука, запис аудиту. Див. `server-after-nonblocking`
   (`.claude/skills/vercel-react-best-practices/rules/server-after-nonblocking.md`). У цьому
   репозиторії `submitLead` (`app/actions.ts`) чекає на `fetch` до n8n синхронно й ігнорує код
   відповіді — це саме той патерн, якого тут уникаємо, не той, який копіюємо.
8. **Що йде в клієнтський код:** якщо дія передає дані назад у клієнтський компонент (не лише
   `status`), перевір, що це не весь запис з бази — див. `server-serialization`
   (`.claude/skills/vercel-react-best-practices/rules/server-serialization.md`).

## Чекліст

```
- [ ] 1. Дія перевіряє сесію/права всередині себе (не лише сторінка через редірект).
- [ ] 2. useActionState + <form action={formAction}>, без preventDefault/fetch з клієнта.
- [ ] 3. Валідація на сервері; клієнтська (якщо є) — лише підказка.
- [ ] 4. label + aria-invalid + aria-describedby на кожному полі з помилкою; підсумок role="alert".
- [ ] 5. Введені значення лишаються після помилки.
- [ ] 6. Дія повертає { status, ... }, не сирий рядок з бази/винятку.
- [ ] 7. Журнали без персональних даних.
- [ ] 8. Повільні побічні ефекти (лист, вебхук, аудит) — в after(), після return стану.
```

## Правила зупинки — зупинись і спитай людину, якщо:

- Форма має надсилати дані на сторонній сервіс (вебхук, email-провайдер) і незрозуміло, чи вже є
  для цього серверний модуль з контрактом (заголовки, підпис, повтори) — не вигадуй свій виклик.
- Задача просить логувати чи показувати в UI дані, які виглядають як персональні (email, телефон,
  IP, вміст повідомлення) без явного дозволу — спитай, чи справді потрібно.
- Незрозуміло, які права потрібні для дії (будь-хто з сесією чи лише певна роль) — не вгадуй.
- Форма має синхронно чекати на відповідь повільного зовнішнього виклику (>1–2с) перед тим, як
  показати користувачу результат — спитай, чи прийнятна затримка, перш ніж вибирати між
  синхронним очікуванням і `after()`.

## Verify — задача готова, лише коли:

- [ ] `npm run lint` і `npm run build` без помилок.
- [ ] Порожня відправка (усі обов'язкові поля пусті) → помилки видно біля полів і в підсумку
      `role="alert"`, значення інших полів не зникли.
- [ ] Відправка з вимкненим JavaScript (DevTools → Disable JavaScript) → форма все одно надсилається
      і сторінка оновлюється зі станом дії.
- [ ] Виклик дії без сесії (наприклад, `curl` напряму на дію без cookie сесії, якщо дія — публічний
      ендпоінт) → відмова, а не виконана зміна.
- [ ] Журнал сервера після відправки — жодних email/телефонів/імен/тексту повідомлення в чистому
      вигляді.
