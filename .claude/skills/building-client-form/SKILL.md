# Building Client Form

Кожна форма в проєктах агенції (заявка, кошторис, зворотний зв'язок, налаштування) робиться за
одним патерном: без нього форми виходять різні на вигляд і поведінку — де без перевірки прав,
де без валідації, де без обробки помилок доступним способом, де користувач бачить "успіх" навіть
коли сервер відповів помилкою.

## Коли застосовувати

- Нова форма, що відправляє дані на сервер (заявка, кошторис, зворотний зв'язок, налаштування,
  нотатка, коментар).
- Переробка існуючої форми: не показує помилки полів, губить введене при помилці, блокує
  інтерфейс на повільній операції (лист, вебхук, аудит-лог).
- **Не** застосовувати: форми пошуку/фільтрації, що не зберігають дані (client-side onChange,
  без Server Action); форми автентифікації/входу (окремий, суворіший патерн безпеки).

## Як робимо

1. **Server Action — публічний POST-ендпоінт.** Усередині самої дії, на самому початку:
   перевірка сесії (`getCurrentUser()`), перевірка прав на дію (правило `server-auth-actions`),
   валідація вхідних даних. Ніколи не покладайся на те, що форму викликає лише твій UI — Server
   Action можна викликати напряму.
2. **`useActionState`** для стану форми на клієнті. Форма повинна працювати і без JavaScript
   (звичайний `<form action={...}>`), `useActionState` лише покращує UX, коли JS є.
3. **Доступні помилки полів.** Кожне поле з помилкою: `aria-invalid="true"`, `aria-describedby`
   веде на елемент з текстом помилки, `<label>` пов'язаний з полем через `htmlFor`/`id`. Підсумок
   усіх помилок форми — в елементі з `role="alert"`, щоб скрінрідер оголосив його одразу.
   Введені значення полів **не зникають** після помилки — повертай їх у стані дії разом з помилками.
4. **Дія повертає лише структурований стан** — `{ status: "ok" | "error" | "<конкретний код>", errors?, values? }`.
   Ніколи не повертай сирий рядок помилки з бази чи стек трейс — це і витік деталей реалізації,
   і непередбачувано для UI.
5. **Жодних персональних даних у журналах.** `console.log`/логи сервера не повинні містити email,
   ім'я, телефон чи вміст повідомлення користувача — лише ідентифікатори (id заявки, id користувача)
   і статуси.
6. **Повільні побічні ефекти — в `after()`.** Лист клієнту, виклик n8n, запис в аудит-лог — усе, що
   не впливає на те, що бачить користувач одразу — винось у `after()` (правило
   `server-after-nonblocking`), щоб відповідь форми не чекала на них.

Правила Vercel, на які спираємось за id (не копіюємо, лише посилаємось):
`server-auth-actions`, `server-after-nonblocking`, `server-serialization`.

## Чекліст
 1. Server Action перевіряє сесію і права всередині себе, не покладаючись на UI.
 2. Форма використовує useActionState і працює без JavaScript.
 3. Кожне поле з помилкою має aria-invalid, aria-describedby, пов'язаний label.
 4. Підсумок помилок форми — в елементі з role="alert".
 5. Введені значення не зникають після помилки.
 6. Дія повертає лише { status, ... } — не рядок з бази, не стек трейс.
 7. Персональні дані користувача не потрапляють у console.log/журнали сервера.
 8. Повільні побічні ефекти (листи, вебхуки, аудит) обгорнуті в after().

## Правила зупинки — зупинись і спитай людину, якщо:

- Незрозуміло, які саме права/роль потрібні для дії (наприклад, чи може будь-який залогінений
  користувач редагувати цей запис, чи лише власник).
- Форма має надсилати дані в зовнішню систему (n8n, email-провайдер), а контракт цієї інтеграції
  не описаний в проєкті — не вигадуй формат запиту сам.
- Потрібно зберігати дані, які виглядають як персональні чи чутливі (паролі, платіжні дані,
  документи) — уточни, як саме їх належить обробляти й де зберігати.

## Verify — задача готова, лише коли:

- [ ] `npm run lint` і `npm run build` без помилок.
- [ ] Порожня відправка форми показує помилки полів, доступні для скрінрідера (`role="alert"`,
      `aria-invalid`, `aria-describedby`), і не втрачає вже введені значення інших полів.
- [ ] Відправка форми з вимкненим JavaScript у браузері все ще працює (звичайний POST).
- [ ] Виклик Server Action без сесії користувача (наприклад, напряму) повертає помилку авторизації,
      а не виконує дію.
- [ ] У журналі сервера після відправки форми немає персональних даних користувача — лише
      ідентифікатори й статус.
