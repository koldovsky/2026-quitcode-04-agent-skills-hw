# Форма клієнта: Server Action + useActionState

Кожен проєкт агенції починається з форми, і кожна форма — це публічний POST-ендпоінт з
персональними даними. Тому форму робимо завжди однаково: безпечно, доступно, швидко й
передбачувано для наступного розробника.

## Коли застосовувати

- Нова форма або зміна наявної, яка щось записує: публічна (заявка, кошторис, контакт) чи
  внутрішня (нотатка до ліда, статус, налаштування workspace).
- Нова чи змінена Server Action, яку викликає форма або кнопка.
- **Не** застосовувати: пошук і фільтри без запису, суто візуальні правки, Route Handlers для
  зовнішніх систем (вебхуки, колбеки) — там свій контракт.

## Як робимо

Файли: логіка розбору й валідації — `lib/<name>-form.ts` (чисті функції, без `"use server"`);
дія — `app/…/actions.ts` з `"use server"`; форма — `components/<name>-form.tsx` з `"use client"`.
Готовий приклад розбору в проєкті — `lib/lead-form.ts` (`parseLeadForm` → `{ ok, data | errors }`).

### 1. Server Action — публічний POST-ендпоінт

Правило Vercel `server-auth-actions`: `proxy.ts` і layout дію **не** захищають — її можна викликати
прямим POST. Порядок усередині дії завжди такий:

1. **Сесія** — для внутрішніх форм: `const user = await getCurrentUser()` з `lib/data.ts`.
2. **Права** — об'єкт належить workspace користувача (`lead.workspaceId === workspace.id`),
   інакше — та сама відповідь, що й «не знайдено». Зразок — `requireOwnLead` в `app/actions.ts`.
3. **Валідація** — `parse<Name>Form(formData)`: `trim`, ліміти довжини (`slice(0, max)` +
   помилка, якщо довше), `enum` — лише зі списку дозволених. Клієнтській валідації не довіряємо.
4. **Запис** у `db`.
5. **Повільне** (лист, n8n, аудит, аналітика) — в `after()` з `next/server`
   (`server-after-nonblocking`): користувач не чекає зовнішню систему.
6. `revalidatePath(...)` для сторінок, що показують змінені дані.

### 2. Відповідь дії — лише стан форми

Тип стану — дискримінований union, спільний для дії й форми:

```ts
export type NoteFormState =
  | { status: "idle" }
  | { status: "invalid"; errors: Partial<Record<NoteField, string>>; values: Partial<Record<NoteField, string>> }
  | { status: "ok" }
  | { status: "error"; message: string };
```

- Ніколи не повертаємо рядок з бази, id сесії, stack trace (`server-serialization`: усе, що
  повертає дія, серіалізується в браузер).
- `values` — лише те, що ввів сам користувач, щоб поля не спорожніли після помилки
  (React 19 скидає неконтрольовану форму після дії).

### 3. Форма — `useActionState`, працює й без JavaScript

```tsx
const [state, formAction, pending] = useActionState(saveNote, { status: "idle" });
<form action={formAction} noValidate>…</form>
```

- `action={formAction}` на `<form>` — без `onSubmit` і `fetch`: без JS форма теж надсилається.
- `pending` → `disabled` і текст кнопки («Зберігаємо…»); повторна відправка неможлива.
- Після `ok` — повідомлення про успіх у `role="status"`.

### 4. Доступні помилки полів

Для кожного поля:

```tsx
<label htmlFor="note-text">Нотатка</label>
<textarea id="note-text" name="text" maxLength={500} defaultValue={values.text}
  aria-invalid={errors.text ? true : undefined}
  aria-describedby={errors.text ? "note-text-error" : undefined} />
{errors.text && <p id="note-text-error">{errors.text}</p>}
```

- Кожне поле має `<label>`; обов'язкові — з `required` (і `aria-required`).
- Над формою — підсумок помилок у `role="alert"` («Перевірте 2 поля»), щоб його почув скрінрідер.
- Тексти помилок — людські й конкретні: що саме виправити.

### 5. Журнали

- Жодних персональних даних у `console.*`: не логуємо `formData`, email, телефон, текст
  повідомлення, IP, тіла запитів/відповідей.
- Можна: назву дії, id запису, код/статус помилки — `console.error("saveNote failed", { leadId, code })`.

## Чекліст

```
- [ ] 1. Дія починається з перевірки сесії й прав (для внутрішніх форм) — до будь-якого запису.
- [ ] 2. Уся валідація — на сервері в parse<Name>Form; ліміти довжини й enum перевірено.
- [ ] 3. Дія повертає лише { status, errors?, values?, message? } — без рядків з бази.
- [ ] 4. Форма: useActionState, <form action={formAction}>, pending блокує кнопку.
- [ ] 5. Кожне поле: label, aria-invalid, aria-describedby → текст помилки; підсумок у role="alert".
- [ ] 6. Після помилки введене лишається (defaultValue з state.values).
- [ ] 7. Листи, n8n, аудит — в after(); відповідь форми не чекає зовнішніх систем.
- [ ] 8. У журналах сервера немає персональних даних і тіл запитів.
```

## Правила зупинки — зупинись і спитай людину, якщо:

- Незрозуміло, **хто** має право надсилати форму (будь-хто, будь-який користувач workspace, лише owner).
- Форма має зберігати нові типи персональних даних (документи, дата народження, платіжні дані) —
  потрібне рішення щодо зберігання й згоди.
- Для задачі треба змінити `proxy.ts`, сесію чи схему автентифікації.
- Побічний ефект має бути **синхронним** (користувач мусить побачити результат зовнішньої системи
  у відповіді форми) — це суперечить `after()`, потрібне інше рішення (статус + колбек).
