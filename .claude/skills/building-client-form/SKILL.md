# Building client forms

Кожен проєкт агенції починається з форми, і кожна форма — це публічний POST-ендпоінт з персональними
даними. Тому форми робимо за одним патерном: однакова безпека, доступність і швидкість у всіх проєктах,
незалежно від того, хто пише — людина чи агент.

## Коли застосовувати

- Нова форма або зміна наявної: поля, валідація, Server Action, повідомлення про помилки чи успіх.
- Скарги «помилок не видно», «не працює без JS», «довго думає», «введене зникає».
- **Не** застосовувати: контракт виклику n8n (заголовки, підпис, колбеки) — це `integrating-n8n-webhooks`;
  суто стилі без зміни поведінки форми.

## Як робимо

Три файли на форму. Еталон у репозиторії — форма заявки: `lib/lead-form.ts`, `app/actions.ts`
(`submitLead`), `components/lead-form.tsx`; бери з неї структуру, але виправляй її відхилення від
цього патерну (доступність, `after()`), а не копіюй їх.

1. **`lib/<name>-form.ts` — поля й валідація.** Тип полів (`type NoteFormField = "text"`), функція
   `parse<Name>Form(formData)` за зразком `parseLeadForm`: `trim()`, обрізання до ліміту, помилки
   як `Partial<Record<Field, string>>` українською, результат `{ ok: true, data } | { ok: false, errors }`.
   Ліміти довжини перевіряй на сервері, `maxLength` в інпуті — лише підказка. Нову бібліотеку
   валідації (zod тощо) не додаємо без згоди людини.

2. **Server Action (`"use server"`) — це публічний POST-ендпоінт.** Будь-хто може викликати його
   напряму, тож усе перевіряємо **всередині** дії, у такому порядку (правило `server-auth-actions`):
   - форма дашборда: `const user = await getCurrentUser()` (`lib/data.ts`, без сесії — редірект на
     `/login`), далі `getWorkspace(user.workspaceSlug)` і перевірка, що об'єкт належить робочому
     простору (`lead.workspaceId === workspace.id`), інакше `{ status: "error" }`;
   - публічна форма: напиши в коментарі над дією, що вона публічна свідомо;
   - потім `parse<Name>Form(formData)`; не пройшло — `{ status: "invalid", errors, values }`;
   - лише потім запис у базу й `revalidatePath(<сторінка>)`. На клієнті не додаємо `router.refresh()`.

3. **Що повертає дія — лише стан форми** (правило `server-serialization`):
   ```ts
   export type NoteFormState =
     | { status: "idle" }
     | { status: "invalid"; errors: Partial<Record<NoteFormField, string>>; values: { text: string } }
     | { status: "ok" }
     | { status: "error"; message: string; values: { text: string } };
   ```
   Значення повертаємо з **кожним** станом невдачі (`invalid` і `error`, напр. «не вдалося зберегти»), щоб
   поле не спорожніло.
   Сигнатура `(prevState: State, formData: FormData) => Promise<State>`. Ніколи не повертаємо рядок з
   бази, об'єкт ліда чи користувача — лише статус, помилки полів і введені користувачем значення.

4. **Клієнтський компонент `components/<name>-form.tsx`** (`"use client"`):
   - `const [state, formAction, pending] = useActionState(action, initialState)`;
   - `<form action={formAction}>` — тоді форма працює й без JavaScript (прогресивне покращення);
     без `onSubmit` + `fetch`;
   - кнопка `disabled={pending}` і текст «Зберігаємо…» під час відправки;
   - **введене не зникає:** React 19 скидає некеровані поля після дії, тому
     `defaultValue={state.status === "invalid" || state.status === "error" ? state.values.text : ""}` і `key`
     на формі, що змінюється разом зі станом (напр. `${state.status}:${state.values.text}`), щоб `defaultValue`
     застосувався після будь-якої невдачі.

5. **Доступні помилки:**
   - у кожного поля видимий `<label htmlFor>` / `id` (не лише `placeholder`);
   - помилка поля — `<p id="<field>-error">`, а в інпуті `aria-invalid={!!error}` і
     `aria-describedby="<field>-error"`, лише коли помилка є;
   - підсумок над формою в `role="alert"` («Перевірте поля: …»), повідомлення про успіх — `role="status"`;
   - `noValidate` на формі лише тоді, коли всі перевірки є на сервері.

6. **Журнали без персональних даних.** Жодного `console.log(formData)` чи значень полів; не пишемо email,
   телефон, ім'я, текст повідомлення чи нотатки. Можна: id запису, назву дії, статус, код помилки.

7. **Повільне — після відповіді.** Листи, виклики n8n, аудит, аналітику загортаємо в `after(async () => …)`
   з `next/server` (правило `server-after-nonblocking`); помилки всередині ловимо й логуємо без
   персональних даних. Як саме викликати n8n — скіл `integrating-n8n-webhooks`.

## Чекліст

```
- [ ] 1. Валідація в lib/<name>-form.ts, ліміти перевіряються на сервері.
- [ ] 2. Дія перевіряє сесію й належність об'єкта ДО валідації й запису (або позначена як публічна).
- [ ] 3. Дія повертає лише { status, errors?, values?, message? } — жодних рядків з бази.
- [ ] 4. useActionState + <form action={formAction}>, без onSubmit/fetch.
- [ ] 5. Кожне поле має label; помилки мають id, aria-invalid і aria-describedby.
- [ ] 6. Є підсумок помилок у role="alert" і повідомлення про успіх у role="status".
- [ ] 7. Після помилки введені значення лишаються в полях.
- [ ] 8. У журналах немає значень полів — лише id і статуси.
- [ ] 9. Листи / n8n / аудит — в after(), відповідь форми їх не чекає.
- [ ] 10. revalidatePath після запису; router.refresh() на клієнті не потрібен.
```

## Правила зупинки — зупинись і спитай людину, якщо:

- незрозуміло, хто має право надсилати форму (публічна, будь-хто з команди, лише певна роль);
- форма зберігає нове поле з персональними даними, якого ще немає в `lib/types.ts`;
- потрібна нова залежність (бібліотека валідації, UI-кіт);
- дані форми мають піти в зовнішній сервіс, про який не домовлено (n8n — лише за скілом
  `integrating-n8n-webhooks`);
- зміна зачіпає `tools/`, `materials/`, `.env*` або вимагає нового секрету.

## Verify — задача готова, лише коли:

- [ ] `npm run lint` і `npm run build` без помилок.
- [ ] Порожня відправка: під полями — помилки, над формою — `role="alert"`; у DevTools → Elements в
      інпуті `aria-invalid="true"` і `aria-describedby`, що вказує на текст помилки.
- [ ] Після помилки (напр. текст довший за ліміт) введене лишилось у полі.
- [ ] DevTools → Settings → Disable JavaScript: відправка працює, сторінка показує помилки чи результат.
- [ ] Дія без сесії: відкрий форму, видали cookie `leaddesk_session` (DevTools → Application),
      надішли — редірект на `/login`, у базі нічого не змінилось.
- [ ] Журнал `npm run dev` після відправки: немає email, телефону, імені чи тексту — лише id і статуси.
- [ ] DevTools → Network → POST форми: час відповіді не включає листи / n8n / аудит.
