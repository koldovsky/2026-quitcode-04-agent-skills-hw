# Виклик n8n з Next.js: деталі

Повернутися до [SKILL.md](../SKILL.md).

## Модуль і ізоляція

- Уся робота з вебхуками n8n — в одному серверному модулі `lib/n8n/client.ts`. Перший рядок —
  `import "server-only"`: якщо Client Component колись імпортує модуль, збірка впаде замість того, щоб
  потягти токен у браузер. Next.js 16 обробляє `server-only` сам, окремий пакет ставити не треба
  (`node_modules/next/dist/docs/01-app/02-guides/data-security.md`, розділ про server-only).
- Змінні `N8N_*` читаються лише тут і в колбек-роуті. Префікс `NEXT_PUBLIC_` вбудовує значення в клієнтський
  бандл, тому для них він заборонений.

## Запит

| Частина | Значення | Навіщо |
|---|---|---|
| Метод і URL | `POST ${N8N_WEBHOOK_BASE_URL}/<event>` | n8n тримає один вебхук на пару «шлях + метод», тож одна подія = один шлях |
| `content-type` | `application/json` | n8n парсить тіло як JSON і віддає наступним вузлам у `$json.body` |
| `x-n8n-token` | `N8N_WEBHOOK_TOKEN` | Header Auth вузла Webhook; хибний або відсутній → n8n відповідає 403 |
| `idempotency-key` | UUID, створений разом із записом | вузол Remove Duplicates у n8n відкидає повтор тієї самої операції |
| `x-correlation-id` | UUID ланцюжка | один ідентифікатор у журналах обох систем |

Ключ ідемпотентності не генерується «на місці» в заголовках: його створює код, що зберігає бізнес-запис
(наприклад, заявку зі статусом `queued`), і передає в клієнт. Тоді і повтор усередині клієнта, і повторна
спроба всієї операції після збою несуть той самий ключ.

## Конверт

```json
{ "version": 1, "event": "lead-created", "data": { "leadId": "lead_0042", "source": "website" } }
```

- `version` піднімаємо лише тоді, коли поле перейменовано або змінило сенс; нове необов'язкове поле версію не змінює.
- `data` — тільки те, що потрібно воркфлоу. Весь рядок із бази, IP, user agent, внутрішні нотатки й сирі
  дані форми не відправляємо: n8n — зовнішня система, а ці дані їй не потрібні.
- `callbackUrl` додаємо лише для асинхронних воркфлоу: `${APP_BASE_URL}/api/n8n/<event>`. Адресу беремо з
  `APP_BASE_URL`, а не із заголовків `Host`/`x-forwarded-host`, які контролює клієнт.

## Таймаут і повтори

- Кожна спроба має власний `AbortSignal.timeout(10_000)` (сигнал створюється всередині циклу: використаний
  сигнал уже «спрацював»). В асинхронному режимі n8n відповідає одразу, тож 10 с без відповіді — це збій.
- Максимум 3 спроби (2 повтори) з паузами 1 с і 3 с — і лише для мережевої помилки, `TimeoutError`, 5xx і 524.
- 4xx не повторюємо: 403 означає хибний токен, 404 — неопублікований воркфлоу або тестовий URL. Повтор
  нічого не виправить, лише створить шум.
- Результат визначаємо за кодом статусу. Текст відповіді Immediately в документації й у коді n8n різний,
  тому на нього не спираємося; з 202 беремо лише `job_id`.

## Хто і коли викликає

- Server Action — публічний POST: сесія, права й валідація всередині (правило Vercel `server-auth-actions`).
- Дія зберігає запис і відповідає користувачу одразу (`{ status, id }`); виклик n8n із повторами — у
  `after()` з `next/server` (правило `server-after-nonblocking`). Next.js виконує Server Actions одного
  клієнта по черзі, тож очікування n8n у дії блокує й наступні дії цього користувача.
- Якщо виклик у `after()` остаточно не вдався — позначаємо запис (`failed`/`retry`), щоб це було видно, а не губилося.
- Інші сервіси чи cron викликають Route Handler, не Server Action.
- `export const runtime = "edge"` не використовуємо: у Next.js 16 Edge Runtime позначено як deprecated
  (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/02-route-segment-config/runtime.md`),
  а підпис колбеків потребує `node:crypto`.

## Журнал виклику

Пишемо: подію, напрям (`out`), `x-correlation-id`, код, тривалість, номер спроби, довжину тіла й sha256 тіла.
Не пишемо: тіло, дані людини, токен, повний URL.
