# Контракт: Next.js → n8n

Деталі до розділу «Контракт коротко» у `SKILL.md`: змінні середовища, вихідний запит, режими відповіді.

## Змінні середовища

Лише серверні. Next.js вбудовує в клієнтський бандл тільки змінні з префіксом `NEXT_PUBLIC_`, тому
жодна змінна `N8N_*` (і `APP_BASE_URL`) цього префікса не має.

| Змінна | Призначення | Значення для локальної розробки |
|---|---|---|
| `N8N_WEBHOOK_BASE_URL` | База production-URL вебхуків; закінчується на `/webhook` | `http://127.0.0.1:5678/webhook` |
| `N8N_WEBHOOK_TOKEN` | Значення заголовка `x-n8n-token` (= Value у credential Header Auth в n8n) | `change-me-webhook-token` |
| `N8N_CALLBACK_SECRET` | Ключ HMAC для підпису колбеків (= Hmac Secret у Crypto credential в n8n) | `change-me-callback-secret` |
| `APP_BASE_URL` | Адреса застосунку, з якої будуємо `callbackUrl` | `http://127.0.0.1:3000` |

- Справжні значення живуть у `.env.local` (git-ignored) і в налаштуваннях хостингу. У git — лише
  `.env.example` з цими чотирма змінними: секрети — `change-me-…`, адреси — локальні, база — `/webhook`.
- Секрет створює людина: `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`.
  Агент значень секретів не вигадує й не виводить.
- Секрет і токен ніколи не потрапляють у query string, Client Component, журнал чи відповідь.
- Якщо в проєкті вже є стара змінна на кшталт `N8N_WEBHOOK_URL` — переходимо на `N8N_WEBHOOK_BASE_URL`
  і прибираємо стару з коду й `.env.example`.

## Де живе код

- Один модуль `lib/n8n/client.ts`, перший рядок — `import "server-only";` (у Next.js 16 пакет
  вбудований, встановлювати не треба). Імпорт модуля з Client Component тоді ламає збірку.
- Жодного `fetch` до n8n і жодного читання `N8N_WEBHOOK_*` поза цим модулем. Server Actions і Route
  Handlers викликають функцію модуля, наприклад `triggerWorkflow(event, data, opts)`.
- Жодного `export const runtime = "edge"`: у Next.js 16 edge застарілий, а підпис потребує `node:crypto`.

## Запит

`POST ${N8N_WEBHOOK_BASE_URL}/<event>`, `<event>` — ім'я події в kebab-case (`lead-created`,
`quote-request`). Одна подія — один шлях: у n8n один вебхук на пару «шлях + метод».

| Заголовок | Значення |
|---|---|
| `content-type` | `application/json` |
| `x-n8n-token` | `N8N_WEBHOOK_TOKEN` |
| `idempotency-key` | UUID бізнес-операції: створюємо **один раз**, зберігаємо разом із записом, у повторах — той самий |
| `x-correlation-id` | UUID ланцюжка дій; той самий пишемо в журнали й очікуємо назад у колбеку |

Тіло — конверт:

```json
{
  "version": 1,
  "event": "quote-request",
  "data": { "quoteId": "q_0042", "company": "Nova Dental", "budget": 1500 },
  "callbackUrl": "http://127.0.0.1:3000/api/n8n/quote-request"
}
```

- `version` — версія формату конверта. Додали необов'язкове поле — версія та сама; перейменували поле
  чи змінили його сенс — нова версія, і воркфлоу певний час приймає обидві.
- `data` — **мінімум**, який потрібен воркфлоу. Не весь рядок з бази: без IP, user agent, внутрішніх
  нотаток, сирих даних форми.
- `callbackUrl` = `${APP_BASE_URL}/api/n8n/<event>` — лише для асинхронних воркфлоу.

## Таймаут і повтори

- Кожна спроба — з `signal: AbortSignal.timeout(10_000)`. В асинхронному режимі n8n відповідає одразу,
  тож 10 с без відповіді — це збій, а не «повільний воркфлоу».
- Повтори: максимум 2 (разом 3 спроби), паузи 1 с і 3 с, **лише** для мережевої помилки, таймауту
  (`TimeoutError`), 5xx і 524. Завжди з тим самим `idempotency-key`.
- 4xx не повторюємо, а показуємо як помилку конфігурації: 403 — неправильний `x-n8n-token`, 404 —
  воркфлоу не опубліковано або це тестовий URL.

## Відповідь n8n

Дивимось лише на **код статусу** (2xx — прийнято; для асинхронного режиму очікуємо 202 з `job_id`).
Текст повідомлення не парсимо й на ньому логіку не будуємо: документація й код n8n формулюють його
по-різному.

## Хто викликає

- Дія з UI — Server Action. Це публічний POST-ендпоінт: сесія, права, валідація — всередині дії
  (правило `server-auth-actions` зі скіла `vercel-react-best-practices`).
- Користувач не чекає на n8n. Дія зберігає запис (напр. `status: "queued"` + `idempotencyKey` +
  `correlationId`), відповідає лише `{ status, id }`, а виклик `triggerWorkflow` з повторами — в
  `after()` (правило `server-after-nonblocking`). Додаткова причина: Next.js виконує Server Actions
  одного клієнта по черзі, тож довге очікування блокує його наступні дії.
- Якщо виклик n8n остаточно не вдався — позначити запис (`status: "failed"`) у тому ж `after()`,
  щоб сторінка статусу це показала.
- Не-React клієнт (інший сервіс, cron) — Route Handler, що викликає той самий модуль.

## Режим відповіді вебхука

| Режим у вузлі Webhook | Що отримує Next.js | Коли |
|---|---|---|
| Immediately | 200 одразу після прийому | подія «до відома», результат не потрібен (`lead-created`) |
| When Last Node Finishes | результат після завершення воркфлоу | лише коротка довідка (секунди) |
| Using «Respond to Webhook» | те, що задасть вузол Respond to Webhook | **стандарт для довгих задач:** 202 `{"job_id": …}` одразу, результат — колбеком |
| Streaming | потік | не використовуємо |

Правило 100 секунд: усе, що може наблизитися до 100 с, — **лише** асинхронно (202 + колбек). На n8n
Cloud вебхук, що не відповів за 100 с, закінчується кодом 524; воркфлоу працює далі, але Next.js про
результат уже не дізнається. Тривалість невідома — вважаємо воркфлоу довгим. Піднімати таймаути
замість колбека — не рішення.

## Тестовий і production URL

| | Тестовий | Production |
|---|---|---|
| Шлях | `/webhook-test/<path>` | `/webhook/<path>` |
| Коли приймає | 120 с після «Listen for test event» у редакторі | поки воркфлоу опублікований |
| Дані видно в редакторі | так | ні |

- У коді й `.env.example` — **лише** `/webhook`. Тестовий URL допустимий тільки тимчасово у власному
  `.env.local` розробника, поки він дивиться дані в редакторі n8n.
- n8n 2.x: production-виклики йдуть в опубліковану версію воркфлоу; після змін його треба опублікувати
  знову.
- Якщо клієнт змінив шляхи (`N8N_ENDPOINT_WEBHOOK` на self-hosted), це фіксуємо в реєстрі інтеграцій
  проєкту `docs/n8n-integrations.md`, а не «підганяємо» код.
