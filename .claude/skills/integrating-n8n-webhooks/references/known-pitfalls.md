# Відомі пастки в документації й чужих скілах

- Документація n8n пише «Workflow got started»; код n8n насправді відповідає
  `{"message":"Workflow was started"}` — тому текст відповіді ніколи не парсимо, дивимось лише код
  статусу.
- Офіційний пакет скілів n8n стверджує, що Header Auth відхиляє запит кодом **401**. Насправді код
  n8n повертає **403** («Authorization data is wrong!»). 401 — для Basic Auth і JWT.
- Той самий пакет пише, що секрет вузла Crypto не прив'язується до credential. Для **Crypto v2** це
  вже не так: і документація, і код використовують Hmac Secret із Crypto credential.
- Приклад вебхука в документації Next.js передає токен у `?token=` GET-запиту й порівнює через
  `!==`; той самий гайд попереджає, що GET-запити можуть кешуватись і потрапляти в журнали. Ми
  робимо суворіше: токен у заголовку, підпис і `crypto.timingSafeEqual`.

## Поза межами цього скіла

- Побудова й зміна воркфлоу в редакторі n8n, експорт чи імпорт JSON воркфлоу.
- Код для вузла Code в n8n.
- Черги й фонові воркери — для наших обсягів вистачає `after()` і колбеків.

## Ліміти, які варто пам'ятати

| Ліміт | Значення |
|---|---|
| Тіло запиту до вебхука n8n | 16 МБ (`N8N_PAYLOAD_SIZE_MAX`) |
| Тіло Server Action | 1 МБ за замовчуванням |
| Відповідь вебхука на n8n Cloud | 100с, далі 524 |
| Тестовий URL | 120с після «Listen for test event» |
| Колбек у Next.js | 64 КБ тіла, вікно часу 300с (наше рішення) |

Файли не передаємо між системами — лише посилання на них.
