# Режими відповіді вебхука і тестовий vs production URL

Читати, коли вирішуєш, чи може форма дочекатися результату, або коли вебхук повертає несподіваний код.

## Режими вузла Webhook

| Режим | Що отримує Next.js | Коли використовуємо |
|---|---|---|
| Immediately | 200 `{"message":"Workflow was started"}` одразу | подія «до відома», результат не потрібен: `lead-created`, аналітика |
| When Last Node Finishes | вихід останнього вузла після завершення | швидка довідка (секунди), коли результат потрібен у відповіді |
| Using Respond to Webhook | те, що задає вузол Respond to Webhook | **стандарт для довгих задач:** 202 `{"job_id": …}` одразу, результат — колбеком |
| Streaming | потік | не використовуємо |

**Правило:** усе, що може наблизитися до **100 секунд**, — лише асинхронно (202 + колбек). На n8n Cloud
запит, на який вебхук не відповів за 100 с, завершується **524**; воркфлоу працює далі, а Next.js про
результат уже не дізнається. Якщо не певний, скільки триває воркфлоу, — він асинхронний.

Respond to Webhook спрацьовує один раз; наступні такі вузли ігноруються. Якщо воркфлоу завершився, не
дійшовши до нього, n8n відповідає 200 зі стандартним повідомленням; помилка до нього — 500.

## Що означає код відповіді вебхука

| Код | Що сталося | Що робимо |
|---|---|---|
| 200 / 202 | прийнято | зберегти `status: "sent"`; чекати колбек (асинхронні) |
| 403 «Authorization data is wrong!» | Header Auth: токен відсутній чи неправильний (не 401 — 401 для Basic/JWT) | не повторювати; перевірити `N8N_WEBHOOK_TOKEN` |
| 404 | воркфлоу не опубліковано, неправильний шлях або **тестовий URL** поза вікном 120 с | не повторювати; перевірити шлях і публікацію |
| 413 | тіло > 16 МБ | не повторювати; надсилати посилання, а не файли |
| 5xx, 524 | збій n8n або Cloud-таймаут | повторити (до 2 разів, 1 с, 3 с) з тим самим ключем |

## Тестовий і production URL

| | Тестовий URL | Production URL |
|---|---|---|
| Шлях | `/webhook-test/<path>` | `/webhook/<path>` |
| Працює | після «Listen for test event» (або запуску воркфлоу) — **120 с** | поки воркфлоу **опублікований** |
| Дані видно в редакторі | так | ні |

- У коді й `.env.example` — **лише** `/webhook`. Тестовий URL можна тимчасово поставити тільки у власний
  `.env.local`, коли дивишся дані в редакторі n8n.
- n8n 2.x: публікація фіксує версію воркфлоу; production-виклики йдуть у неї, а не в останні правки. Після
  змін — Publish знову.
- На self-hosted шляхи змінюються змінними `N8N_ENDPOINT_WEBHOOK` / `N8N_ENDPOINT_WEBHOOK_TEST`. Якщо клієнт
  це зробив — записати в `docs/n8n-integrations.md` проєкту.

## Мок для локальної розробки

`scripts/mock-n8n.mjs` цього скіла (копія `tools/mock-n8n.mjs`) поводиться як Webhook + Respond to
Webhook + HTTP Request з підписом:

```bash
node .claude/skills/integrating-n8n-webhooks/scripts/mock-n8n.mjs --help
node --env-file=.env.local .claude/skills/integrating-n8n-webhooks/scripts/mock-n8n.mjs --mode respond-202 --delay 5000
#   N8N_WEBHOOK_TOKEN у .env.local → вимагає x-n8n-token (403 без нього)
#   N8N_CALLBACK_SECRET у .env.local → через 5 с підписаний колбек на callbackUrl із запиту
node .claude/skills/integrating-n8n-webhooks/scripts/mock-n8n.mjs --mode slow --cloud-timeout 5000     # 524, як на Cloud
```

Журнал мока: метод, шлях, статус, тривалість, **імена** заголовків, розмір і sha256 тіла, `auth=`,
`idempotency=new|repeat|absent`. Тіл і значень він не друкує. `/webhook-test/<path>` мок приймає лише з
`--listen` і лише 120 с.
