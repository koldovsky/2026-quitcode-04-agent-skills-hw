# Режими відповіді вебхука n8n

Повернутися до [SKILL.md](../SKILL.md).

| Режим вузла Webhook | Що отримує Next.js | Коли беремо |
|---|---|---|
| Immediately | 200 одразу після отримання | подія «до відома», результат не потрібен (`lead-created`, аналітика) |
| When Last Node Finishes | вихід останнього вузла | швидка довідка на секунди, коли результат потрібен у відповіді |
| Using Respond to Webhook | те, що поверне вузол Respond to Webhook | **стандарт для довгих задач**: 202 `{"job_id": …}` одразу, результат — колбеком |
| Streaming | потік | не використовуємо |

## Правило 100 секунд

На n8n Cloud запит, на який вебхук не відповів за 100 с, закінчується кодом 524, а воркфлоу працює далі —
Next.js про його результат уже не дізнається. Тому все, що може наблизитися до 100 с, — лише асинхронно
(202 + колбек). Невідома тривалість = асинхронно.

Вузол Respond to Webhook спрацьовує один раз. Якщо воркфлоу закінчився, не дійшовши до нього, n8n відповідає
200 зі стандартним повідомленням; помилка до нього — 500 (для нас це «повторити»). Тому для воркфлоу з колбеком
успіх — лише 202 з `job_id`, а 200 — «колбека не буде», запис одразу `failed`. Рідкісний виняток: відповідь на першу
спробу загубилась (таймаут, 5xx проксі), а повтор із тим самим `idempotency-key` Remove Duplicates відкинув — 200,
хоча перша спроба працює. Запис тоді на час стане `failed`, а колбек першої спроби знайде його за
`requestIdempotencyKey` і переведе в `ready`; пізній `failed` ніколи не перетирає `ready`. Ми свідомо обрали
хибне «не вдалося» на хвилину замість запису, що вічно чекає.

## Тестовий і production URL

| | Тестовий | Production |
|---|---|---|
| Шлях | `/webhook-test/<event>` | `/webhook/<event>` |
| Працює | 120 с після «Listen for test event» у редакторі | поки воркфлоу опублікований |
| Дані видно в редакторі | так | ні |

- У коді й `.env.example` — лише `/webhook`. Тестовий URL — тільки тимчасово у власному `.env.local`, коли
  дивитесь дані в редакторі; заявки на нього губляться, щойно хтось закриє редактор.
- У n8n 2.x публікація фіксує версію воркфлоу: після змін — опублікувати знову.
- Self-hosted n8n може перейменувати шляхи (`N8N_ENDPOINT_WEBHOOK`, `N8N_ENDPOINT_WEBHOOK_TEST`) — тоді це
  записуємо в `docs/n8n-integrations.md` проєкту.

## Ліміти

| Що | Ліміт |
|---|---|
| тіло запиту до вебхука n8n | 16 МБ (`N8N_PAYLOAD_SIZE_MAX` на self-hosted) |
| тіло Server Action | 1 МБ за замовчуванням (`serverActions.bodySizeLimit`) |
| відповідь вебхука на n8n Cloud | 100 с, далі 524 |
| тестовий URL | 120 с |
| колбек у Next.js | 64 КБ і вікно часу 300 с (рішення команди) |

Файли не передаємо — лише посилання на них.
