# Режими відповіді вебхука n8n і URL

## Режими (вузол Webhook → Respond)

| Режим | Що отримує Next.js | Коли |
|---|---|---|
| Immediately | `200` одразу після отримання | подія «до відома»: `lead-created`, аналітика |
| When Last Node Finishes | вихід останнього вузла після завершення | швидка довідка (секунди), результат потрібен у відповіді |
| Using 'Respond to Webhook' Node | те, що задає Respond to Webhook | **стандарт для довгих задач:** `202 {"job_id": …}` одразу, результат — колбеком |
| Streaming | потік | не використовуємо |

**Правило 100 секунд.** Усе, що може наблизитися до 100 с, — лише асинхронно (202 + колбек). На n8n
Cloud запит, на який вебхук не відповів за 100 с, завершується **524**; воркфлоу працює далі, а Next.js
про результат уже не дізнається. Не знаєш, скільки триває воркфлоу, — він асинхронний.

Respond to Webhook спрацьовує один раз, наступні такі вузли ігноруються. Воркфлоу завершився, не
дійшовши до нього, — `200` зі стандартним повідомленням; помилка до нього — `500`.

## Тестовий і production URL

| | Тестовий | Production |
|---|---|---|
| Шлях | `/webhook-test/<path>` | `/webhook/<path>` |
| Коли працює | 120 с після «Listen for test event» у редакторі | поки воркфлоу **опублікований** |
| Дані видно в редакторі | так | ні |

- У коді й `.env.example` — лише `/webhook`. Тестовий URL — тимчасово й лише у власному `.env.local`.
- n8n 2.x: публікація фіксує версію воркфлоу; production-виклики йдуть у неї, а не в останні правки.
  Після змін — Publish знову.
- Self-hosted n8n може перейменувати шляхи (`N8N_ENDPOINT_WEBHOOK`, `N8N_ENDPOINT_WEBHOOK_TEST`) —
  тоді це записуємо в `docs/n8n-integrations.md`.

## Коди, які повертає n8n

| Код | Причина | Дія |
|---|---|---|
| `200` | Immediately / Last Node | для асинхронної події — помилка налаштування, не повторювати |
| `202` + `job_id` | Respond to Webhook | успіх асинхронної події |
| `403` «Authorization data is wrong!» | Header Auth: немає або неправильний `x-n8n-token` | не повторювати, перевірити токен |
| `404` | воркфлоу не опубліковано, неправильний шлях або тестовий URL без «Listen» | не повторювати |
| `5xx`, `524` | збій / таймаут Cloud | повторити з тим самим `idempotency-key` |

## Відомі пастки

- «Workflow got started» (документація) проти `Workflow was started` (код) — текст відповіді не парсимо.
- Офіційний пакет n8n-скілів пише, що Header Auth відхиляє з 401; код n8n повертає **403**. 401 — для Basic
  Auth і JWT.
- Той самий пакет пише, що секрет вузла Crypto не прив'язується до credential; для Crypto v2 це вже не так.
- Приклад вебхука в документації Next.js передає токен у `?token=` у GET і порівнює через `!==` —
  ми робимо суворіше: токен у заголовку, підпис і `timingSafeEqual`.
