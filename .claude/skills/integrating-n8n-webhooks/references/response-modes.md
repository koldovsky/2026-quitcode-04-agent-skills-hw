# Режими відповіді вебхука, тестовий і production URL, ліміти

## Режим відповіді (Response mode) вузла Webhook

| Режим | Що отримує Next.js | Коли використовуємо |
|---|---|---|
| Immediately | 200 одразу після отримання запиту | Подія «до відома», результат не потрібен: `lead-created`, аналітика |
| When Last Node Finishes | Вихід останнього вузла після завершення воркфлоу | Швидкий запит довідки (секунди), результат потрібен у відповіді |
| Using Respond to Webhook | Те, що задає вузол Respond to Webhook | **Стандарт для довгих задач:** 202 `{"job_id": …}` одразу, результат — колбеком |
| Streaming | Потік | Не використовуємо |

**Правило 100 секунд.** Усе, що може наблизитися до 100 с, — лише асинхронно (202 + колбек). На n8n
Cloud запит, на який вебхук не відповів за 100 с, завершується **524**; воркфлоу працює далі, а Next.js
про результат уже не дізнається. **Не певен, скільки триває воркфлоу, — він асинхронний.**

Respond to Webhook спрацьовує один раз (наступні ігноруються). Воркфлоу завершився, не дійшовши до
нього, — 200 зі стандартним повідомленням; помилка до нього — 500.

Який режим обрати для події:
- «до відома», результат не потрібен → Immediately; виклик у `after()`, без `callbackUrl`;
- триває секунди й результат потрібен одразу → When Last Node Finishes (але все одно з таймаутом 10 с);
- десятки секунд і довше (PDF, генерація, зовнішні API) → Respond to Webhook 202 + колбек.

## Тестовий і production URL

| | Тестовий | Production |
|---|---|---|
| Шлях | `/webhook-test/<path>` | `/webhook/<path>` |
| Коли працює | 120 с після «Listen for test event» | Поки воркфлоу **опублікований** |
| Дані видно в редакторі | Так | Ні |

- У коді й `.env.example` — **лише** `/webhook` (перевірка C1). Тестовий URL — тимчасово й лише у
  власному `.env.local`, коли дивишся дані в редакторі n8n.
- n8n 2.x: публікація фіксує версію воркфлоу; production-виклики йдуть у неї, не в останні правки.
  Після змін — Publish знову.
- На self-hosted шляхи можна змінити (`N8N_ENDPOINT_WEBHOOK`, `N8N_ENDPOINT_WEBHOOK_TEST`) — тоді це
  записуємо в `docs/n8n-integrations.md` проєкту.

## Ліміти

| Ліміт | Значення |
|---|---|
| Тіло запиту до вебхука n8n | 16 МБ (`N8N_PAYLOAD_SIZE_MAX`) |
| Тіло Server Action | 1 МБ за замовчуванням (`serverActions.bodySizeLimit`) |
| Відповідь вебхука на n8n Cloud | 100 с, далі 524 |
| Тестовий URL | 120 с після «Listen for test event» |
| Колбек у Next.js | 64 КБ, вікно часу 300 с (наше рішення) |

Файли не передаємо — лише посилання.

## Журнали

| Пишемо | Не пишемо ніколи |
|---|---|
| подію, напрям, `x-correlation-id` | тіло запиту чи відповіді |
| код статусу, тривалість, номер спроби | ім'я, email, телефон, IP клієнта |
| довжину тіла і його sha256 | токен, підпис, секрет, повний URL з query string |

Відповіді з помилкою не містять внутрішніх подробиць (стек, SQL, URL n8n). Перевірка C14.

## Відомі пастки в документації й чужих скілах

- «Workflow got started» (документація) проти `Workflow was started` (код n8n) — текст не парсимо.
- Офіційний пакет скілів n8n пише, що Header Auth відхиляє з **401**; код n8n повертає **403**
  («Authorization data is wrong!»). 401 — для Basic Auth і JWT.
- Той самий пакет пише, що секрет вузла Crypto не прив'язується до credential. Для Crypto v2 це не так:
  використовується Hmac Secret із Crypto credential.
- Приклад вебхука в документації Next.js передає токен у `?token=` GET-запитом і порівнює `!==`.
  Ми суворіше: токен у заголовку, підпис, `timingSafeEqual`.
