# Колбек n8n → Next.js: точний порядок обробки

Ендпоінт: `POST /api/n8n/<path>` — Route Handler `app/api/n8n/[event]/route.ts`. Це публічний
HTTP-ендпоінт — довіряємо лише підпису, нічому іншому.

| Заголовок | Значення |
|---|---|
| `content-type` | `application/json` |
| `x-n8n-timestamp` | Unix-час у секундах, коли n8n підписав запит |
| `x-n8n-signature` | `sha256=<hex HMAC-SHA256(N8N_CALLBACK_SECRET, "${timestamp}.${rawBody}")>` |
| `idempotency-key` | `<data.jobId>:<event>` — ті самі значення, що в підписаному тілі |
| `x-correlation-id` | Скопійований із запиту, що запустив воркфлоу |

Тіло:
```json
{ "version": 1, "event": "quote-request.completed", "data": { "jobId": "5f0c…", "status": "completed", "correlationId": "9b1e…", "requestIdempotencyKey": "c3d4…", "result": { "documentUrl": "https://files.example.test/n8n/5f0c….pdf" }, "completedAt": "2026-09-21T12:00:00.000Z" } }
```
`data.status` — `completed` або `failed` (тоді замість `result` — `error: { code }`).

## Порядок обробки — саме такий, крок за кроком

1. Подія зі шляху (`[event]`) невідома → **404**; `content-type` не `application/json` → **415**.
   Обидві — ще до читання тіла.
2. Прочитати тіло як **сирий текст** (`await req.text()`, лише один раз). Ніякого `req.json()` чи
   `JSON.parse` до перевірки підпису — повторна серіалізація змінює байти, підпис не зійдеться.
3. Тіло більше 64 КБ → **413**.
4. `x-n8n-timestamp` відрізняється від поточного часу більш ніж на **300 секунд** (у будь-який бік)
   → **401** (захист від replay; n8n цього вікна не задає, це наше рішення).
5. Порахувати HMAC від `${timestamp}.${raw}`, порівняти з підписом: спершу довжини, потім
   `crypto.timingSafeEqual` (кидає на різних довжинах) — **не `===`**. Не збіглось → **401** без
   подробиць у тілі.
6. «Застовпити» `idempotency-key` унікальним записом у БД/KV. Вже був → **200** `{"duplicate": true}`
   — n8n більше не повторюватиме, дані не зміняться вдруге.
7. Лише тепер `JSON.parse(raw)` і перевірка форми: подія в тілі відповідає шляху, а
   `idempotency-key` дорівнює `${data.jobId}:${event}` із тіла — інакше **400**. (Заголовок
   `idempotency-key` підписом НЕ захищений — HMAC рахується лише від `timestamp.raw`; тому звірка з
   тілом на цьому кроці — саме те, що не дає підмінити ключ у межах вікна.)
8. Зберегти мінімальний стан (напр. `status = ready`, посилання на документ) **до** відповіді. Якщо
   обробка впала на кроці 7–8 — **звільнити** `idempotency-key`, інакше законний повтор від n8n
   (Retry On Fail) отримає фальшивий `{"duplicate": true}`, і результат загубиться назавжди.
9. Відповісти **202** `{"ok": true}`.
10. Повільне (листи, сповіщення, інтеграції) — у `after()`.

Сховище для `idempotency-key` — база чи KV з унікальним обмеженням; пам'ять процесу годиться лише
для демо (serverless-обробники не ділять стан між запитами).

## Ідемпотентність з обох боків

- Next.js → n8n: той самий `idempotency-key` у кожній спробі; в n8n одразу за Webhook стоїть
  **Remove Duplicates** («Remove Items Processed in Previous Executions», ключ `idempotency-key`).
- n8n → Next.js: n8n повторює колбек через Retry On Fail; Next.js відсікає повтори за
  `idempotency-key` (крок 6) і приймає лише ключ, що збігається з підписаним тілом (крок 7).

## Журнали

| Пишемо | Не пишемо ніколи |
|---|---|
| подію, напрям, `x-correlation-id` | тіло запиту чи відповіді |
| код статусу, тривалість, номер спроби | ім'я, email, телефон, IP клієнта |
| довжину тіла і його sha256 | токен, підпис, секрет, повний URL з query string |

Відповіді з помилкою не містять внутрішніх подробиць (стек, SQL, URL n8n).
