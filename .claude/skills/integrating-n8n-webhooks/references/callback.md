# Колбек n8n → Next.js

Route Handler `app/api/n8n/[event]/route.ts` — публічний HTTP-ендпоінт. Довіряємо лише підпису.

## Що приходить

| Заголовок | Значення |
|---|---|
| `content-type` | `application/json` |
| `x-n8n-timestamp` | Unix-час (секунди) підпису |
| `x-n8n-signature` | `sha256=` + hex HMAC-SHA256(`N8N_CALLBACK_SECRET`, `` `${timestamp}.${rawBody}` ``) |
| `idempotency-key` | `` `${data.jobId}:${event}` `` — з тих самих значень, що в підписаному тілі |
| `x-correlation-id` | з запиту, що запустив воркфлоу |

```json
{ "version": 1, "event": "quote-request.completed",
  "data": { "jobId": "5f0c…", "status": "completed", "correlationId": "9b1e…",
            "requestIdempotencyKey": "c3d4…",
            "result": { "documentUrl": "https://files.example.test/n8n/5f0c….pdf" },
            "completedAt": "2026-09-21T12:00:00.000Z" } }
```

`data.status` — `completed` або `failed` (тоді `error: { code }` замість `result`). Мок надсилає
лише `completed`. `data.requestIdempotencyKey` — ключ вихідного запиту: за ним знаходимо запис.

## Порядок обробки

| # | Крок | Відповідь при збої |
|---|---|---|
| 1 | `[event]` зі шляху невідомий | 404 |
|   | тип медіа з `content-type` (до `;`, без урахування регістру) не рівно `application/json` — `application/jsonp` теж (обидві перевірки — до читання тіла) | 415 |
| 2 | Сире тіло читається один раз і з лімітом **під час читання**: `content-length` > 64 КБ — одразу 413; інакше потік через `TransformStream`, що рахує байти, → `.text()` (у шаблоні — `readRawBody`); **ні** `request.json()`, **ні** `JSON.parse` до підпису | — |
| 3 | тіло більше 64 КБ — за `content-length` або щойно прочитано 64 КБ + 1 байт (потік скасовується) | 413 |
| 4 | `x-n8n-timestamp` відрізняється від «зараз» більш ніж на 300 с у будь-який бік | 401 |
| 5 | HMAC від `` `${timestamp}.${raw}` `` порівняти з підписом: спершу довжини, потім `crypto.timingSafeEqual` (на різних довжинах він кидає помилку). Не `===` | 401, без подробиць |
| 6 | Застовпити `idempotency-key` (унікальний запис). Уже був | 200 `{"duplicate":true}` |
| 7 | `JSON.parse(raw)` і перевірка форми; `event` у тілі — `<[event]>.<щось>`; ключ = `` `${data.jobId}:${event з тіла}` ``; `data.status` — `completed` (з `result`) або `failed` (з `error`) | 400 |
| 8 | Зберегти мінімальний стан (напр. `status: "ready"`, `documentUrl`) **до** відповіді. Збій на 7–8 → **звільнити** ключ | 400 / 500 |
| 9 | Відповідь | 202 `{"ok":true}` |
| 10 | Листи, сповіщення, інші інтеграції | в `after()` |

## Чому саме так

- **Сире тіло до підпису.** Будь-яка повторна серіалізація (`JSON.parse` → `JSON.stringify`)
  змінює байти (пробіли, порядок, екранування) — HMAC не зійдеться. Тому n8n і підписує, і
  відправляє один і той самий рядок.
- **Ліміт під час читання, а не після.** `await request.text()` спершу читає все тіло в пам'ять —
  розмір можна порахувати лише потім. Підроблений запит без `content-length` (chunked) тримав би
  роут і пам'ять, поки шле байти. Тому байти рахуються, поки надходять, і на 64 КБ + 1 читання
  зупиняється.
- **`timingSafeEqual`, а не `===`.** Звичайне порівняння рядків виходить на першому розбіжному
  символі — за часом відповіді можна підбирати підпис.
- **Вікно 300 с.** Проти відтворення перехопленого колбека пізніше. Документація n8n вікна не
  задає — це наше рішення.
- **Ключ звіряємо з тілом.** Заголовок `idempotency-key` підписом не захищений (HMAC — лише від
  `timestamp.raw`). Інакше перехоплений колбек можна було б у межах вікна надіслати ще раз з
  новим ключем і обробити вдруге. Коли ключ мусить дорівнювати полям підписаного тіла, повтор із
  тим самим ключем — дублікат, з іншим — 400.
- **Запис до відповіді.** Отримавши 2xx, n8n колбек не повторить. Якби критичний запис жив лише
  в `after()` і впав, результат загубився б.
- **Звільнити ключ при збої.** Інакше Retry On Fail в n8n отримає `{"duplicate":true}` на повтор,
  і результат загубиться.
- **Сховище ключів** — база чи KV з унікальним обмеженням. Пам'ять процесу — лише для демо:
  на serverless обробники не ділять стан.
- **Шлях і заголовки — у журнал лише перевіреними.** До кроку 5 усе в запиті пише будь-хто:
  невідомий `[event]` журналюємо як `unknown`, а `x-correlation-id` — лише у формі UUID
  (інакше `invalid`, без заголовка — `none`). Так підроблений запит не пише в журнал довільний
  текст.

## Ідемпотентність з обох боків

- Next.js → n8n: той самий `idempotency-key` у всіх спробах; в n8n за Webhook — Remove Duplicates.
- n8n → Next.js: Retry On Fail повторює колбек; Next.js відсікає повтори (крок 6) і приймає лише
  ключ, що збігається з тілом (крок 7). Дублікати неминучі з обох боків — це не «бонус».

## Швидка ручна перевірка

- Повторити той самий колбек (ті самі заголовки й тіло) → 200 `{"duplicate":true}`, стан не
  змінився вдруге.
- Змінити один байт тіла або підпису → 401.
- `x-n8n-timestamp` на 10 хв у минулому (з правильним підписом) → 401.
- Тіло, переформатоване після підпису (інші пробіли) → 401.
