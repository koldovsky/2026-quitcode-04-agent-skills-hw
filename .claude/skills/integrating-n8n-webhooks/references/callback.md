# Колбек n8n → Next.js: чому саме такий порядок

Повернутися до [SKILL.md](../SKILL.md). Самі кроки — у SKILL.md; тут — причини й наслідки.

## Що захищаємо

Колбек-роут — публічний HTTP-ендпоінт: будь-хто може надіслати POST на `/api/n8n/<event>`. Довіряємо лише
підпису HMAC, який уміє поставити тільки той, хто знає `N8N_CALLBACK_SECRET`.

## Причини кроків

- **404/415 до читання тіла.** Невідома подія чи не-JSON — відповідь без витрат на читання й підпис.
- **Сире тіло (`req.text()`).** Підпис рахується від точних байтів. `req.json()` і повторна серіалізація
  змінюють пробіли й порядок — підпис не зійдеться, а спокуса «перевірити після парсингу» відкриває обхід.
  Тіло Request читається один раз, тому читаємо саме текстом.
- **64 КБ.** Колбек несе статус і посилання, не файли; більше тіло — помилка або атака. Ліміт тримаємо під час
  читання: Route Handler власного ліміту тіла не має, а chunked-запит без `content-length` інакше змусив би
  буферизувати все тіло ще до перевірки підпису.
- **Вікно ±300 с.** Захист від повторного відтворення старого підписаного запиту. Вікно — рішення команди,
  n8n його не задає; перевіряємо в обидва боки.
- **Довжина, потім `timingSafeEqual`.** `===` завершується на першому незбіжному символі й «підказує» час;
  `timingSafeEqual` порівнює за сталий час, але кидає виняток на буферах різної довжини — тому спершу довжини.
  Відповідь 401 — без пояснень, що саме не зійшлося.
- **Claim ключа до парсингу.** n8n повторює колбек (Retry On Fail), тож дублікати неминучі. Унікальний запис
  ключа в БД/KV відсікає повтор: 200 `{"duplicate": true}` — n8n бачить успіх і більше не повторює. Тому 200
  лише для ключа, чий результат **уже збережено**: поки перша доставка ще пише (наприклад, n8n не дочекався
  відповіді й повторив), повтор отримує 409 — для Retry On Fail це помилка, і він спробує ще. Інакше перша
  доставка могла б упасти й звільнити ключ уже після того, як n8n прийняв «дублікат» за успіх. Стан «в обробці»
  має термін (~60 с, більше за будь-яку нормальну обробку): якщо обробник упав між claim і завершенням, не
  звільнивши ключ (таймаут serverless-функції), прострочений ключ можна застовпити знову — інакше кожен повтор
  n8n отримував би 409, доки той не здасться.
- **Ключ звіряємо з тілом.** Заголовок `idempotency-key` підписом не покритий (HMAC — лише від
  `${timestamp}.${raw}`). Хто перехопив підписаний колбек, міг би в межах вікна надіслати ті самі байти з новим
  ключем. Коли ключ мусить дорівнювати `${data.jobId}:${event}` з підписаного тіла, такий трюк дає 400.
- **Стан до відповіді.** Отримавши 2xx, n8n колбек не повторить. Якби критичний запис жив лише в `after()` і
  впав, результат загубився б. Тому `status = ready` і посилання зберігаємо до 202, а листи — в `after()`.
- **Звільнення ключа.** Якщо після claim обробка впала (400 на перевірці форми, 5xx на записі), ключ
  звільняємо: інакше повтор n8n отримає `duplicate`, і результат не збережеться ніколи.

## Коди відповідей

| Ситуація | Код |
|---|---|
| невідома подія в шляху | 404 |
| `content-type` не `application/json` | 415 |
| тіло > 64 КБ (заявлене чи під час читання) | 413 |
| тіло обірвалось під час читання | 400 |
| немає/прострочений `x-n8n-timestamp`, хибний підпис | 401 |
| повтор уже обробленого ключа | 200 `{"duplicate": true}` |
| повтор ключа, який ще обробляється | 409 (n8n повторить) |
| тіло не тієї форми, подія не та, ключ ≠ `${data.jobId}:${event}` | 400 |
| прийнято й збережено | 202 `{"ok": true}` |

## Відповідність назв

- Сегмент шляху: `<event>` (наприклад `lead-enriched`).
- `event` у тілі колбека: `<event>.completed`; результат — у `data.status`: `completed` (з `result`) або
  `failed` (з `error: { code }`).
- `idempotency-key` колбека: `${data.jobId}:${event з тіла}`, наприклад `5f0c…:lead-enriched.completed`.
- Запис, до якого належить колбек, шукаємо за полями **підписаного** тіла: `data.jobId` (збережений з
  відповіді 202) або `data.requestIdempotencyKey` (наш ключ вихідного запиту, n8n повертає його назад).

## Сховище ключів

База чи KV з унікальним обмеженням. Пам'ять процесу — лише для демо й локальної розробки: на serverless
обробники не ділять стан.
