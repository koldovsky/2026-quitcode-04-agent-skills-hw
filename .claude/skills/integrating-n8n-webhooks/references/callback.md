# Колбек n8n → Next.js

Ендпоінт `POST /api/n8n/<path>` — Route Handler `app/api/n8n/[event]/route.ts`. Route Handler —
публічний HTTP-ендпоінт: довіряємо **лише підпису**, не сесії й не IP.

## Заголовки

| Заголовок | Значення |
|---|---|
| `content-type` | `application/json` |
| `x-n8n-timestamp` | Unix-час у **секундах**, коли n8n підписав запит |
| `x-n8n-signature` | `sha256=<hex HMAC-SHA256(N8N_CALLBACK_SECRET, "${timestamp}.${rawBody}")>` |
| `idempotency-key` | `<data.jobId>:<event>` — ті самі значення, що в підписаному тілі |
| `x-correlation-id` | скопійований із запиту, що запустив воркфлоу |

## Тіло

```json
{
  "version": 1,
  "event": "quote-request.completed",
  "data": {
    "jobId": "5f0c…",
    "status": "completed",
    "correlationId": "9b1e…",
    "requestIdempotencyKey": "c3d4…",
    "result": { "documentUrl": "https://files.example.test/n8n/5f0c….pdf" },
    "completedAt": "2026-09-21T12:00:00.000Z"
  }
}
```

`data.status` — `completed` або `failed` (тоді замість `result` — `error: { code }`). Шлях `[event]` —
ім'я події (`quote-request`), `event` у тілі — `<path>.completed` / `<path>.failed`.
Запис знаходимо за `data.requestIdempotencyKey` (ключ, який ми згенерували й зберегли з записом) або за
`jobId`, який записали з відповіді `202 {"job_id"}`.

## Порядок обробки — саме такий

1. Подія зі шляху невідома → **404**; `content-type` не `application/json` → **415**. Обидві — до
   читання тіла.
2. Тіло — **сирим текстом**: `const raw = await request.text()`. Ні `request.json()`, ні `JSON.parse`
   до перевірки підпису: повторна серіалізація змінює байти, і підпис не зійдеться. Тіло читається раз.
3. Більше 64 КБ (`Buffer.byteLength(raw)`) → **413**.
4. `x-n8n-timestamp` відрізняється від поточного часу більш ніж на **300 с** у будь-який бік (або не
   число) → **401**. Захист від повторного відтворення; вікно — наше рішення.
5. HMAC від `` `${timestamp}.${raw}` ``, порівняння з підписом: спершу довжини, потім
   `crypto.timingSafeEqual` (він кидає на різних довжинах). **Не** `===` / `!==`. Не збігається → **401**
   без подробиць у тілі.
6. «Застовпити» `idempotency-key` (унікальний запис). Вже був → **200** `{"duplicate": true}`.
7. Тепер `JSON.parse(raw)` і перевірка форми. Не та форма, подія в тілі не відповідає шляху або
   `idempotency-key` ≠ `` `${data.jobId}:${event}` `` з тіла → **400** (і звільнити ключ).
8. Зберегти мінімальний стан (`status = ready`, `documentUrl`) **до** відповіді. Якщо після кроку 6
   обробка впала (4xx/5xx на кроках 7–8) — **звільнити** ключ, інакше Retry On Fail n8n отримає
   `{"duplicate": true}` і результат загубиться.
9. Відповісти **202** `{"ok": true}`.
10. Повільне (листи, сповіщення, інтеграції) — в `after()`.

## Чому так

- **Запис до відповіді:** отримавши 2xx, n8n не повторить. Якщо критичний запис жив би лише в `after()` і
  впав, результат загубився б назавжди.
- **Ключ звіряємо з тілом:** заголовок `idempotency-key` не підписаний (HMAC — лише від
  `${timestamp}.${raw}`). Хто перехопив підписаний колбек, міг би в межах 300 с надіслати ті самі байти з
  новим ключем. Коли ключ мусить дорівнювати полям підписаного тіла, повтор із тим самим ключем —
  дублікат, з іншим — 400.
- **Сховище ключів** — база чи KV з унікальним обмеженням. Пам'ять процесу — лише для демо (у нашому
  LeadDesk «база» теж у пам'яті, тож для демо це чесно; на serverless обробники стан не ділять).
- **Ідемпотентність з обох боків:** наші повтори й Retry On Fail n8n роблять дублікати неминучими. В n8n
  одразу за Webhook — Remove Duplicates за `idempotency-key`; у Next.js — кроки 6–7.

## Відповіді з помилкою

Коротке тіло без внутрішніх подробиць: `{"error": "invalid signature"}`, `{"error": "unknown event"}` —
без стека, SQL, URL n8n, очікуваного підпису.
