# Колбек: n8n → Next.js

Деталі до кроків про ендпоінт колбека в `SKILL.md`: що приходить, у якому порядку перевіряти, як
відсікати повтори.

## Ендпоінт

`POST /api/n8n/<event>` — Route Handler `app/api/n8n/[event]/route.ts`, один на всі події; `<event>` —
той самий шлях, що й у вихідному запиті (`quote-request`). Route Handler — публічний HTTP-ендпоінт,
тож довіряємо **лише підпису**, а не cookie, IP чи «секретному» URL.

## Що надсилає n8n

| Заголовок | Значення |
|---|---|
| `content-type` | `application/json` |
| `x-n8n-timestamp` | Unix-час у **секундах**, коли n8n підписав тіло |
| `x-n8n-signature` | `sha256=` + hex від HMAC-SHA256 з ключем `N8N_CALLBACK_SECRET` над рядком `` `${timestamp}.${rawBody}` `` |
| `idempotency-key` | `` `${data.jobId}:${event}` `` — ті самі значення, що в підписаному тілі, напр. `5f0c…:quote-request.completed` |
| `x-correlation-id` | скопійований із запиту, що запустив воркфлоу (може бути відсутній) |

```json
{
  "version": 1,
  "event": "quote-request.completed",
  "data": {
    "jobId": "5f0c…",
    "status": "completed",
    "correlationId": "9b1e…",
    "requestIdempotencyKey": "c3d4…",
    "result": { "documentUrl": "https://files.example.test/n8n/5f0c….pdf" },
    "completedAt": "2026-09-21T12:00:00.000Z"
  }
}
```

- `event` у тілі — `<шлях>.completed` або `<шлях>.failed`; для `failed` замість `result` —
  `error: { code }`. Локальний мок надсилає лише `completed`.
- Запис у нашій базі знаходимо за `data.requestIdempotencyKey` (ключ, який ми згенерували й надіслали
  у вихідному запиті) або за `data.correlationId`. `jobId` — ідентифікатор n8n, його зберігаємо поруч.

## Порядок обробки — саме такий

| Крок | Що робимо | Відповідь, якщо не так |
|---|---|---|
| 1 | Подія зі шляху не з нашого списку (`["quote-request"]`); `content-type` не `application/json`. Обидві перевірки — **до** читання тіла | **404** / **415** |
| 2 | `content-length` більше за 64 КБ → відразу **413**, тіло не читаємо | **413** |
| 3 | Тіло — сирим текстом, але **потоком з лімітом** 64 КБ (`request.body.getReader()`, зупинитись і `cancel()`, щойно ліміт перевищено; колбек несе посилання, не файли). Тіло читається один раз; **ні** `req.json()`, **ні** `JSON.parse` до кроку 5 — повторна серіалізація змінює байти, і підпис не зійдеться. Не `request.text()`: воно спершу вантажить усе тіло в пам'ять (тут ми свідомо суворіші за перший варіант записки команди, де було `req.text()` + перевірка розміру — ліміт 64 КБ має діяти до читання, а не після; `check-contract.mjs` C10 дає FAIL на `request.text()`) | **413** |
| 4 | `x-n8n-timestamp` — ціле число, і `Math.abs(now - ts) <= 300` секунд (в обидва боки; захист від replay) | **401** |
| 5 | `expected = "sha256=" + HMAC(secret, `${ts}.${raw}`)`; порівняти з заголовком: спершу **довжини** буферів, потім `crypto.timingSafeEqual` (на різних довжинах він кидає виняток). Не `===` / `!==` | **401**, тіло без подробиць |
| 6 | «Застовпити» `idempotency-key` в сховищі з унікальністю (insert-if-absent). Уже є | **200** `{"duplicate": true}` |
| 7 | Лише тепер `JSON.parse(raw)` (помилка розбору — теж **400**, не 500) і перевірка форми під час виконання, а не лише типом TypeScript: `data.status` дорівнює суфіксу `event` (`completed`/`failed`), `requestIdempotencyKey` — непорожній рядок, для `completed` — обов'язковий непорожній `result.documentUrl`, `error.code` — рядок, якщо є; `version === 1`, `event` дорівнює `` `${шлях}.completed` `` або `.failed`, `data.jobId` — рядок, заголовок `idempotency-key` === `` `${data.jobId}:${event}` `` | **400** (+ звільнити ключ) |
| 8 | Зберегти мінімальний стан **до** відповіді: `status = "ready"` / `"failed"`, `documentUrl`, `jobId`, `completedAt`. Запис не знайдено або збереження впало — звільнити ключ | **404** / **500** (+ звільнити ключ) |
| 9 | Відповісти | **202** `{"ok": true}` |
| 10 | Повільне (лист клієнту, сповіщення, інтеграції) — в `after()` (правило `server-after-nonblocking`) | — |

## Чому саме так

- **Запис до відповіді (крок 8).** Отримавши 2xx, n8n колбек не повторює. Якби критичний запис жив лише
  в `after()` і впав, результат загубився б назавжди.
- **Звільнення ключа.** Якщо після кроку 6 обробка впала, повтор n8n (Retry On Fail) отримав би
  `duplicate` і результат загубився б. Тому на 4xx/5xx після кроку 6 ключ видаляємо.
- **Ключ звіряємо з тілом (крок 7).** Заголовок `idempotency-key` підписом не захищений (HMAC — лише від
  `${timestamp}.${raw}`). Той, хто перехопив підписаний колбек, міг би в межах 300 с надіслати ті самі
  байти з новим ключем. Коли ключ мусить дорівнювати полям підписаного тіла, той самий ключ — дублікат,
  інший — 400.
- **Помилки без подробиць.** 401/400/500 не містять стеку, URL n8n чи того, що саме не зійшлося.

## Сховище ключів

- Прод: таблиця чи KV з унікальним обмеженням на ключ (`INSERT … ON CONFLICT DO NOTHING`, `SET NX`),
  з датою — ключі старші за кілька днів можна чистити.
- Демо / in-memory база проєкту: `Map` або `Set` на рівні модуля бази годиться **лише для демо** — на
  serverless обробники не ділять пам'ять між запитами. Позначте це коментарем у коді.

## Ідемпотентність з обох боків

- Next.js → n8n: один `idempotency-key` на бізнес-операцію в усіх спробах; у воркфлоу одразу після
  Webhook стоїть Remove Duplicates за цим ключем.
- n8n → Next.js: Retry On Fail у вузлі HTTP Request повторює колбек; ми відсікаємо повтори на кроці 6
  і приймаємо лише ключ, що збігається з підписаним тілом (крок 7).
- Дублікати неминучі з обох боків, тож ідемпотентність — обов'язкова частина, а не бонус.
