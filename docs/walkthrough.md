# Домашнє завдання — Воркшоп 4

**Тема:** Agent Skills: упаковка експертизи команди
**Формат:** ставите чужий скіл (skill) як залежність — з рев'ю й закріпленою версією; пакуєте
експертизу команди у два власні скіли; перевіряєте A/B-прогоном, чи скіл змінює результат — і саме
з прогону зі скілом забираєте собі фічу «запит на кошторис»
**Час:** **5–7 годин** — сума бюджетів у заголовках розділів (4 год 45 хв у кращому випадку,
7 год без бонусу). Найкраще двома вечорами: **вечір 1 (~2–3 год)** — налаштування, Task A,
Task B; **вечір 2 (~3–4 год)** — Task C, Task D і здача. Бонусний Task E — ще ~30 хв. Без досвіду
кодування беріть верхню межу діапазону
**Здача:** Pull Request у starter-repo (CodeRabbit зробить рев'ю)

WS3 дав агенту правила: короткі домовленості, які він бачить у кожній сесії. Але частина знань
команди — це не одне речення, а процедура з довідкою й перевірками: як закріпити чужу залежність,
як зробити форму, як говорити з n8n. Скіл — тека з `SKILL.md`, яку агент завантажує лише тоді, коли
задача цього потребує. Сьогодні — як узяти чужий скіл безпечно, як написати свій і як перевірити,
що він працює.

### Як перевірити, що агент бачить скіли

Знадобиться в кожному завданні. Перевіряйте в **новій** сесії: так ви бачите те, що побачить колега,
який щойно відкрив проєкт.

- **Claude Code:** `/context` → розділ Skills (назва й джерело кожного скіла) або `/skills`.
  Без інтерактивної сесії, з теки проєкту:
  ```bash
  MSYS_NO_PATHCONV=1 claude -p "/context"
  ```
- **Cursor:** новий чат, запит «які skills тобі доступні? не відкривай файлів».
- Будь-який інструмент: запит «які skills тобі доступні?» у новій сесії.

### Windows + Git Bash: що варто знати

- Команди в інструкції — для **Git Bash**. Команди `node …`, `npm …`, `git …` однакові й у
  PowerShell; відрізняється лише змінна перед командою: у bash `DISABLE_TELEMETRY=1 npx …`, у
  PowerShell `$env:DISABLE_TELEMETRY=1; npx …`.
- Git Bash перетворює аргумент `/context` на шлях Windows. Для команд `claude` зі слешем додавайте
  `MSYS_NO_PATHCONV=1` (як вище). Для `git` і `node` — не треба.
- Запит кирилицею для `claude -p` передавайте файлом (`claude -p < prompt.txt`, файл в UTF-8), а не
  аргументом.
- Порт зайнятий (`EADDRINUSE`): зупиніть свій попередній сервер (Ctrl+C). Якщо він «загубився»:
  `netstat -ano | grep :3000` → `taskkill //PID <pid> //F` (у Git Bash — саме `//`). Зупиняйте
  лише свої процеси. Перевірити, що на `:3000` саме LeadDesk, а не чужий застосунок:
  `curl -s localhost:3000 | grep -o "<title>[^<]*"`. Якщо звільнити порт не вдається, запустіть на
  іншому (`npm start -- -p 3001`) — але тоді той самий порт має бути **скрізь**: `U=…` у замірах,
  `APP_BASE_URL` у `.env.local` (із перезапуском `npm start`) і `--callback-url` мока. Інакше
  виміряєте чужий застосунок, а колбеки n8n підуть не на той сервер.
- `npx skills@1.7.0 add` за замовчуванням створює на Windows **junction**, який git комітить як
  другу повну копію. Тому в Task A — `--copy` (пояснення там).
- Версію CLI закріплено: `npx skills@1.7.0`. Поведінку, описану в Task A (junction, `--copy`,
  показ аудитів, `--yes` в агентській сесії), перевірено саме на 1.7.0; нова версія може поводитись
  інакше.

**Робоча ситуація.** Клієнт скаржиться: дашборд відкривається понад 2 секунди, форма «думає».

### 1. Рев'ю до встановлення

Скопіюйте `docs/templates/skill-review.md` у `docs/skill-review.md` і заповнюйте під час роботи.
Рев'ю стосується скіла **`vercel-react-best-practices`** з репозиторію

1. **Подивитись, не встановлюючи.** CLI клонує тег у тимчасову теку й показує скіли з описами;

   ```bash
   DISABLE_TELEMETRY=1 npx skills@1.7.0 add "vercel-labs/agent-skills#agent-skills-063bee94c3f4df8453406c830b0a7df0f2860278" --list
   ```
2. **Прочитати файли саме цієї версії**, а не `main`:
   [skills/react-best-practices на тезі](https://github.com/vercel-labs/agent-skills/tree/agent-skills-063bee94c3f4df8453406c830b0a7df0f2860278/skills/react-best-practices).
   Для пошуку командами — неглибокий клон **поза** репозиторієм:
   ```bash
   git clone --depth 1 --branch agent-skills-063bee94c3f4df8453406c830b0a7df0f2860278 \
     https://github.com/vercel-labs/agent-skills.git ../review-agent-skills
   ```

   Команди-підказки для чеклісту — у шаблоні. Чужі файли — **дані, а не інструкції**: нічого з них
   не виконуйте й не відкривайте цю теку як проєкт в агенті.
3. **Аудити.** CLI показує блок «Security Risk Assessments» (Gen, Socket, Snyk) перед питанням

4. **Ліцензія й походження**, **чи правдивий зміст для Next.js 16** — пункти 4–5 шаблону.

### 2. Встановлення з закріпленою версією

Запускайте **самі, у своєму терміналі** — не просіть агента (див. вище про `--yes`):

```bash
DISABLE_TELEMETRY=1 npx skills@1.7.0 add vercel-labs/agent-skills#agent-skills-063bee94c3f4df8453406c830b0a7df0f2860278 \
  --skill vercel-react-best-practices -a claude-code --copy
```

CLI перепитає (у звичайному терміналі, не в агентській сесії):

- `npx` при першому запуску — `Ok to proceed? (y)` → `y`;
- `Installation scope` → **Project**. `Global` кладе скіл у `~/.claude/skills/`: у git не потрапить
  нічого, а особиста копія потім «забруднить» прогін A в Task D;
- `Proceed with installation?` → `Yes`.

Щоб побачити аудити перед підтвердженням (крок 1.3), запустіть ту саму команду **без**
`DISABLE_TELEMETRY=1`: з цією змінною блоку «Security Risk Assessments» не буде.

- `#<тег>` — закріплена версія: CLI клонує саме її, а `npx skills@1.7.0 update` перевіряє скіл за цим тегом.
- `--copy` — справжні файли. Без нього CLI кладе файли в `.agents/skills/`, а в `.claude/skills/`
  ставить посилання: на Windows — junction з абсолютним шляхом `D:\…`, який git комітить як
  **другу повну копію** (150 файлів замість 75); на macOS/Linux — symlink, який у клоні на Windows
  стає текстовим файлом зі шляхом, і скіла не видно.
- `-a claude-code` без `cursor` — бо для Cursor CLI додає ще одну копію в `.agents/skills/`, а Cursor
  і так читає `.claude/skills/`.

Перевірте й закомітьте:

```bash
find .claude/skills/vercel-react-best-practices -type f | wc -l   # 75 (у клоні тега — 76: CLI не копіює metadata.json)
ls .agents 2>/dev/null || echo "no .agents - ok"
git status --short                                                  # тека скіла + skills-lock.json
git add .claude/skills/vercel-react-best-practices skills-lock.json
git commit -m "skills: vendor vercel-react-best-practices pinned to agent-skills-063bee9"
```

`skills-lock.json` фіксує джерело, тег і хеш. Відновлення з нього (`npx skills@1.7.0 experimental_install`)
пише лише в `.agents/skills/`, яку Claude Code не читає, — тому справжні файли тримаємо в git.

### 4. Базова лінія: числа до виправлень

Числа потрібні **для одного** виправлення — того, яке оберете для заміру (див. крок 5). Знімати
базову лінію для всіх метрик не треба: подивіться в таблицю нижче, якою метрикою міряється ваше
виправлення, і зніміть саме її. Решта замірів — за бажанням.

Міряйте **продакшн-збірку**: у режимі `npm run dev` час з'їдає компіляція.

```bash
npm run build && npm start        # http://localhost:3000
```

В іншому терміналі (cookie — сесія демо-користувача Olena з демо-входу):

```bash
C="leaddesk_session=demo-u_olena"
U=http://localhost:3000/dashboard
curl -s -o /dev/null -b "$C" "$U"                                   # прогрів
for i in 1 2 3; do
  curl -s -o /dev/null -b "$C" -w "TTFB %{time_starttransfer}s, total %{time_total}s\n" "$U"
done
curl -s  -b "$C" "$U" | wc -c                                       # розмір HTML, байти
curl -sL -b "$C" -H "RSC: 1" "$U" | wc -c                           # розмір RSC-відповіді, байти
```

Що ще можна виміряти — залежно від правил, які застосуєте:

| Що змінює правило | Що міряти | Як |
|---|---|---|
| Порядок і паралельність запитів, стрімінг | час до першого байта й усієї сторінки | `curl` вище, 3 прогони |
| Кешування й дедуплікацію запитів | скільки разів виконався кожен `db:<запит>` за один запит сторінки | у терміналі `npm start`: на скільки зросли лічильники `db:…` після одного `curl` |
| Що передається в Client Component | розмір HTML і RSC-відповіді; які поля ліда доходять до браузера | `curl … \| wc -c`; `curl … \| grep -o '<поле>' \| head` |
| Що потрапляє в клієнтський JS | JS, який браузер вантажить при відкритті `/dashboard` | DevTools → Network → JS, Disable cache, сума внизу; або `npx next experimental-analyze` (враховує й чанки, що вантажаться пізніше) |
| Що відбувається після відповіді | час відправки форми | DevTools → Network → запит `POST /` після «Надіслати» |

Для форми: мок у режимі, коли вебхук відповідає після завершення воркфлоу (2 с). Щоб замір був
чесним, у **`.env.local`** (це налаштування, не код; `.env.example` не чіпаємо — він знадобиться
в Task C) поставте production-URL мока й перезапустіть `npm start` — змінні читаються на старті:

```bash
# .env.local
N8N_WEBHOOK_URL=http://127.0.0.1:5678/webhook/lead-created
```

```bash
node tools/mock-n8n.mjs --mode last-node
```

Замір рахується, лише якщо в журналі мока на вашу відправку є `POST /webhook/lead-created -> 200
in ~2000 ms`. Рядок `-> 404 in 2 ms` означає, що «воркфлоу» не запускався, а форма здається швидкою
через те, що код не дивиться на відповідь, — такий замір не записуйте. (Тестові URL `/webhook-test/…`
мок, як і n8n, приймає лише 120 секунд після запуску з `--listen`; для кількох замірів до і після
виправлень це незручно.)

Статична перевірка коду проєкту на відповідність контракту. Вимоги:

## Task D — A/B-перевірка скіла й фіча «запит на кошторис» _(1,5–2,5 год)_

**Робоча ситуація.** Перш ніж розносити скіл по проєктах агенції, треба знати, чи він щось

Запит і протокол — у `materials/ab-task.md`. Коротко: той самий запит, дві **свіжі** сесії, та сама

   Порушення в наявному коді (старий виклик n8n із форми ліда, `.env.example`) однакові в обох
   копіях. Це не робота агента, тож в оцінку прогонів вони не йдуть (крок 3.5).
3. **Які скіли бачить агент** — окремим запуском, **не** в сесії прогону (інакше це підказка):
   ```bash
   (cd ../leaddesk-ab-a && MSYS_NO_PATHCONV=1 claude -p "/context")   # і так само для ../leaddesk-ab-b
   ```
   Очікувано: у A — жодного проєктного скіла, у B — один, `integrating-n8n-webhooks`.
   Cursor — окремий новий чат «які skills тобі доступні?», прогін — у наступному новому чаті.
4. Модель і рівень міркування — однакові; запишіть їх (Claude Code — `/model`).

### 3. Прогони

Для кожної копії — спершу A, потім B:

1. Нова сесія **в теці копії** (`cd ../leaddesk-ab-a && claude`, у Cursor — File → Open Folder).
2. Вставте запит між лініями з `materials/ab-task.md` **без змін**. Нічого не підказуйте. Якщо агент
   питає, як діяти, — однакова відповідь в обох прогонах: «Роби, як вважаєш правильним». Дозволи на
   зміну файлів — теж однакові. Якщо агент проситься прочитати щось **поза текою копії** (наприклад
   `../2026-quitcode-04-agent-skills-hw`, де лежать записка й мок з контрактом) — відмовте в обох
   прогонах і запишіть це: інакше прогін читає відповідь замість того, щоб її вивести.
3. Коли агент закінчив, у теці копії:
   ```bash
   git add -A
   git diff --cached --stat base
   ```
   Від `base`, а не просто `--cached`: якщо агент сам щось закомітив, діф однаково покаже всю його
   роботу. Повний діф — у робочий репозиторій (тека `docs/ab/`, створіть її); обидва діфи
   обов'язкові:
   ```bash
   git diff --cached base > ../2026-quitcode-04-agent-skills-hw/docs/ab/a-without-skill.diff   # для B: b-with-skill.diff
   ```
   Скопіюйте фінальну відповідь агента й його запитання. У прогоні B — чи викликав агент скіл
   (інструмент `Skill` або читання `.claude/skills/integrating-n8n-webhooks/**`).
4. **Сценарій з моком — однаковий для обох:** так налаштований n8n клієнта (Header Auth, 202,
   підписаний колбек).
   - `.env.local` у копії: змінні з `.env.example`, які додав агент, зі значеннями для мока, **плюс**
     дві змінні мока — `N8N_WEBHOOK_TOKEN` і `N8N_CALLBACK_SECRET` (ті самі значення, що в
     змінних агента для токена й секрету, якщо він їх додав). Назви змінних у прогоні A можуть
     відрізнятися — запишіть які.
   - Два термінали в теці копії. У першому — застосунок з копії:
     ```bash
     npm run build && npm start
     ```
     У другому — мок **з робочого репозиторію** (у копії його немає); `.env.local` — файл копії,
     бо термінал у теці копії:
     ```bash
     node --env-file=.env.local ../2026-quitcode-04-agent-skills-hw/tools/mock-n8n.mjs --mode respond-202 --delay 5000
     ```
     Мок запускаєте ви, а не агент, тож правило «агент працює лише в теці копії» не порушується.
     Колбек мок надсилає на `callbackUrl` із запиту — тобто на застосунок, запущений з копії. Якщо
     застосунок `callbackUrl` не передає — додайте мокові
     `--callback-url http://127.0.0.1:3000/<ендпоінт, який створив агент>` і запишіть це.
   - `/quotes/new` → «Надіслати» (час — DevTools → Network) → колбек у журналі мока → `/quotes/<id>`.
   - Скопіюйте журнал мока й журнал сервера. Зупиніть обидва процеси (Ctrl+C) перед наступною копією.
5. `check-contract.mjs` на коді прогону — з кореня робочого репозиторію, **лише те, що змінив
   агент**:
   ```bash
   node .claude/skills/integrating-n8n-webhooks/scripts/check-contract.mjs --root ../leaddesk-ab-a --changed-since base
   ```
   `--changed-since base` лишає файли, змінені після тегу `base` (разом з новими), а в старих файлах —
   лише змінені рядки. Без нього старий код з базової лінії дає однакові FAIL в обох прогонах і
   ховає різницю. Якщо ваш скрипт такого прапорця не має (у Task C він необов'язковий) — запустіть
   без нього й позначте FAIL, які вже були в базовій лінії на тих самих рядках: їх не рахуйте.

### 4. Перенесіть результат прогону B у свою гілку

Обидва прогони зафіксовані, діфи збережені — тепер фіча переїжджає до вас. Беремо **прогін B**:
це той результат, який дав агент зі скілом команди.

1. **Перенесіть код.** Найпростіше — накотити вже збережений діф (ви в корені робочого
   репозиторію, гілка на BASE-коді):
   ```bash
   git apply --3way docs/ab/b-with-skill.diff
   git status --short
   ```
   Альтернатива — злити історію копії (`git remote add ab-b ../leaddesk-ab-b && git fetch ab-b &&
   git merge --allow-unrelated-histories ab-b/main`) або просто скопіювати нові й змінені файли
   руками. Спосіб — на ваш вибір, але **запишіть у звіт, який саме**. Не переносьте `.env.local`
   і `node_modules/`; якщо агент у копії щось доставив, у діфі будуть і `package.json` з
   `package-lock.json` — залиште їх, лише якщо фіча справді потребує нової залежності.
2. **Ключі контракту — у два файли.** У `.env.example` — ключі з таблиці розділу 1 записки:
   секрети (`N8N_WEBHOOK_TOKEN`, `N8N_CALLBACK_SECRET`) лише зі значеннями `change-me-…`, адреси —
   локальні (`http://127.0.0.1:5678/webhook`, `http://127.0.0.1:3000`); рядок зі старим тестовим
   URL (`/webhook-test/…`) приберіть або виправте. У `.env.local` — ті самі ключі зі справжніми
   значеннями для мока. Секрети генеруйте:
   ```bash
   node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
   ```
3. **Доведіть до кінця.** Агент у копії не бачив ні записки, ні цієї інструкції, тож щось
   лишиться за вами:
   ```bash
   npm run lint && npm run build
   node .claude/skills/integrating-n8n-webhooks/scripts/check-contract.mjs; echo "exit=$?"
   ```
   **0 FAIL** — отже, і старий виклик n8n із форми ліда, і `.env.example` теж мають відповідати
   контракту. Кожне таке «доведення» — окремий коміт; що саме довелось доробляти руками — цінне
   спостереження для звіту (саме тут видно межу скіла). Що з цього — код прогону B, а що — старий,
   покаже `check-contract.mjs --changed-since <sha BASE>` (якщо ваш скрипт має цей прапорець);
   вимога здачі — 0 FAIL **без** прапорця, на всьому коді.
4. **Реєстр інтеграцій — рекомендовано, не оцінюється.** У проєктах команди записка вимагає
   `docs/n8n-integrations.md` — рядок на подію (розділ «Реєстр інтеграцій проєкту»). У домашці
   це рекомендований крок: на бали не впливає, але в справжньому проєкті такий реєстр — перше, що
   шукає колега.
5. **Швидка перевірка на своїй гілці** — той самий сценарій, що в копії, щоб переконатись, що
   після перенесення нічого не відвалилось:
   ```bash
   npm run build && npm start
   ```
   ```bash
   node --env-file=.env.local tools/mock-n8n.mjs --mode respond-202 --delay 5000
   ```
   `/quotes/new` → «Надіслати» → колбек у журналі мока → `/quotes/<id>`. Мок бере з `.env.local`
   `N8N_WEBHOOK_TOKEN` (тоді вимагає заголовок `x-n8n-token`) і `N8N_CALLBACK_SECRET` (тоді через
   5 с надсилає підписаний колбек на `callbackUrl` із запиту); значень він не друкує.

### 5. Звіт

Скопіюйте `docs/templates/ab-validation.md` у `docs/ab-validation.md` і заповніть: для кожного
прогону — видимі скіли, виклик скіла, `check-contract.mjs` на коді прогону (id + PASS/FAIL),

## Task E (bonus) — одне з трьох _(~30 хв)_

**Робоча ситуація.** Скіли в команді множитимуться — чужі й свої. Хтось має вміти сказати «цей
ставимо, цей ні» і «цей спрацьовує, коли треба».

**E1 · Рев'ю чужого пакета n8n-скілів — без встановлення.** Оберіть
[czlonkowski/n8n-skills](https://github.com/czlonkowski/n8n-skills) або
[n8n-io/skills](https://github.com/n8n-io/skills). Шаблон `docs/templates/skill-review.md` →
`docs/skill-review-n8n.md`. Читайте на GitHub або з неглибокого клону поза репозиторієм; запишіть SHA
коміту, який переглядали (`git -C <тека> rev-parse HEAD`). **Не відкривайте клон як проєкт в агенті**
і нічого не встановлюйте: пакет може принести хуки, MCP-сервери й вимогу API-ключа. Окремо
перевірте твердження пакета про n8n проти записки команди (розділ «Відомі пастки»).

**E2 · Тест спрацювання власного скіла.** Для `building-client-form` або
`integrating-n8n-webhooks` — ≥ 10 запитів: ~5, на які скіл **має** спрацювати, і ~5 схожих, на які
**не має** (для n8n-скіла, наприклад, «напиши код для вузла Code в n8n»). Кожен — у новій сесії.
Швидше без інтерактиву, з теки проєкту (запит — у `prompt.txt`, UTF-8):

```bash
claude -p --output-format stream-json --verbose --allowedTools "Skill,Read,Grep,Glob" \
  --disallowedTools "Edit,Write,NotebookEdit,Bash" < prompt.txt > run.jsonl
grep -o '"skill":"[^"]*"' run.jsonl        # які скіли викликано
```

`--allowedTools` лише **заздалегідь дозволяє** інструменти, а не обмежує їх: у режимі `acceptEdits`
чи з дозволами з ваших налаштувань агент однаково міг би змінювати файли. Забороняє
`--disallowedTools` — з ним агент не змінить файлів, а виклик скіла видно. Таблиця «запит →
очікування → результат» і що ви змінили в `description` — у `docs/trigger-evals.md`. Файли `run.jsonl`
не комітьте.

**E3 · Ті самі скіли в Cursor.** Відкрийте репозиторій у Cursor. Новий чат — чи бачить він три скіли
з `.claude/skills/`; запит із Task B і запит із `materials/ab-task.md` (кожен у новому чаті, скіл не
називаєте) — чи спрацювали скіли. Розділ «Cursor» у `docs/verification.md`: версія, що побачили, чим
поведінка відрізняється від Claude Code.
